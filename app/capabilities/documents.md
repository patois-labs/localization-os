---
module: documents
title: Documents and the editor
summary: Documents are the actual content - upload a file, translate it, review the segments a person needs to look at, and export it back in its original format.
nouns:
  Project: "The container. It has one source language, one or more target languages, and belongs to a customer."
  Document: "One uploaded file inside a project - docx, pptx, txt, html, md, po, srt, json, xlsx, idml, xml, DITA, DocBook, resx, Android strings.xml, a MadCap Flare project zip, epub, csv/tsv, icml, OpenDocument, Visio, CAT bilingual files and about 85 formats in all (GET /api/formats lists them)."
  Segment: "One sentence-sized unit of the document, per target language. This is what gets translated, scored, flagged and approved."
  Segmented mode: "The document is split into segments and translated unit by unit. The normal mode."
  Full-text mode: "The document is treated as one block. Used where segmenting would destroy meaning; it has its own paragraph-level repair tools."
  Status: "Where a segment stands - untranslated, translated, needs review, approved."
  Document status: "Derived from the segments of every language, never set by hand: new (nothing translated), in translation (some segments still untouched), in review (everything translated, not everything approved), done (every segment approved). Shown on the document page, the project page, `doc list`, `doc show`, `project show` and the API as `status`."
  QA flag: "A specific machine-found problem on a segment - a glossary or DNT violation, damaged inline tags, a number that changed, a refusal, an output-language mismatch, or model commentary that leaked into the translation."
  Inline tag: "A formatting marker carried through translation. Damaged tags are the main reason a segment is held back."
  Editor: "The side-by-side review screen - source, target, TM suggestions, QA findings, approve."
  Export: "Rebuilding the translated file in its original format."
verbs:
  Add content: "Web: the project page -> upload. CLI: `doc upload <project_id> <file>`."
  Fill from memory first: "Web: Apply 100% TM matches on the document page (free - no model call). CLI: `doc apply-tm <doc_id> <locale>`."
  Machine-translate it: "Web: on the document page the buttons name the language they act on (Translate de-DE live, Translate de-DE in background, Apply 100% TM matches to de-DE) and a one-line hint says what each does; Translate all N languages starts one background job per language. API: POST /api/documents/{id}/translate with a `targets` list. CLI: `doc translate <doc_id> --locale de-DE` (synchronous, one language at a time)."
  Run a whole workflow over it: "Web: the run-workflow control on the document page. CLI: `workflow run`."
  Review and correct: "Web: the editor - fix the target, then approve. Approving writes the pair to TM and applies the target to the document's other open repeats of that source (they show a Propagated badge; Unlink repeats keeps one out). CLI: `doc show <doc_id> --detail` lists per-segment status and flags headlessly."
  See why a segment is held: "Web: the QA cell in the editor names the finding. CLI: `doc show 12 --detail` reports the same flags."
  Raise a query on a segment: "Web: the editor row carries a `query` button (when the Queries feature is on) that opens a thread scoped to that segment, so a question is asked where the content is. It links to the /queries thread view; see the Queries card for the lifecycle, the vendor round trip and the email-only notification limits."
  Log an LQA finding: "A reviewer records an MQM finding (dimension, severity, note) on a segment. Web: the LQA scorecard page (`/documents/{id}/lqa`) has a Reviewer findings section to log/edit/withdraw them, and each editor/LQA row shows its segment inline. /api + CLI: `lqa log|findings|edit|withdraw` and POST|GET /api/documents/{id}/lqa/findings + POST /api/lqa/findings/{fid}[/withdraw]. Reviewer+ (edit/withdraw own-row or manager+). A human finding feeds the qa report but NEVER changes the machine LQA score or a workflow gate; withdraw is a soft delete (the row is kept). Running a scoring is web-only - the `lqa` CLI/API group manages FINDINGS, it does not run a scoring. Opening the scorecard page never calls the LLM judge (a page view is free and instant). The headline is the authoritative saved scoring: the latest workflow LQA run's DURABLE score+gate (computed against that step's own threshold), or - if only a manual Re-score exists - that ad-hoc scoring's worst-segment score with NO gate, or 'no findings on record' when nothing is saved. The persisted machine findings (workflow-run + ad-hoc) are shown read-only below; `lqa findings --document <id> --machine` reads the same headline+findings in-process. The page also runs live structural + rulebook checks for this view, clearly labelled as not the gate. The LLM judge (fluency/accuracy/style/terminology) runs only on 'Re-score & save'. If a configured judge fails to return a verdict during a re-score, the scoring is HELD: the previous scoring is preserved (nothing is overwritten) and the page says 'LLM judge unavailable - previous scoring preserved'. In a workflow, an unavailable judge holds the LQA step at needs_review (StepRun error notes 'judge unavailable') and TERMINATES the run at that step - it never drives the on_fail fix loop nor falls through to downstream steps, so a judge outage is never scored as a clean pass, never mistaken for a quality failure worth re-fixing, and never more permissive than a real failing judge."
  Fix broken formatting: "Web: the 'fix tags' control on a segment. CLI: `tagging repair` (prints an estimate; add `--yes` to run it)."
  Get the file back: "Web: download/export on the document or project page. CLI: `doc export <doc_id> --locale de-DE`, or `project export <id> --zip` for a whole delivery bundle."
  Search past translations: "Web: the concordance search. CLI: `tm search`."
needs:
  - "A customer and a project with the target languages you want. A document cannot exist outside a project."
  - "A live engine, unless you are only applying TM. Without one everything comes back as mock placeholder text."
  - "For a workflow run: a workflow that can produce the target you are running (a grouped workflow picks its per-language variant by the run's languages)."
limits:
  - "A translation run in which some segments failed (for example an engine outage mid-run) ends FAILED, not completed: the job error names how many segments failed and the first engine error, the translated segments stay saved, and the export of that locale is HELD (409, or skipped and reported in a bundle) until the failed segments are retried. Retry failed segments by running translate again (web Translate, CLI doc translate, API POST translate, MCP translate): it picks up only the untranslated segments. allow_held ships the source-filled file explicitly."
  - "Untouched files come back exactly as uploaded: exporting a language into which nothing has been translated returns the stored original byte for byte, with no language stamp added (PDF, Angular XMB and Trados packages, whose deliverable is a different file, are always rebuilt). A translated file keeps the original's byte-order mark and line endings."
  - "Plural forms: on export, a target language that needs more plural forms than the source (Polish, Russian, Arabic and others) gets every missing or empty form filled with the plural translation (the singular only where the target's rule means one), in gettext PO, i18next JSON, Qt .ts, Rails YAML, Fluent and ARB alike; forms a file already has are never replaced. Refine per-form wording in a PO editor if you want it."
  - "Export is guarded. A document whose inline tags could not be verified is EXCLUDED from a delivery bundle and listed in _QUARANTINED.txt - loudly, on purpose."
  - "A milder failure is substitution: a damaged unit is exported as its SOURCE text so the file stays well-formed. Those units are visibly untranslated rather than invisibly broken, and they are reported per document (_SUBSTITUTED.txt, a warning line, and export headers)."
  - "Segments held for review are still counted as translated by the light counts. Use the detailed view if you need to know how many a person still has to look at."
  - "A segment whose numbers changed, whose tags broke, or that carries leaked model commentary is routed to needs-review and held out of TM. Those badges clear automatically when a later clean save fixes the text."
  - "Full-text mode has a different repair story from segmented mode - per-paragraph views, reverts and hand edits - and its source-fallback escape hatch is capped by an install-wide share ceiling, refused above it rather than warned."
  - "A full-text export whose translated body has a different real paragraph count than the source - fewer, more, or a blank stored body - is REFUSED, not silently source-filled: it would ship English source under a target-locale filename. A count desync leaves no trustworthy positional map, so there is no override here (unlike the tagged inline-tag case); re-run the translation or edit the body. A run whose output was implausibly short for its input fails loudly for the same reason - a green deliverable that is mostly untranslated is the failure this prevents."
  - "Text files (.txt, .srt/.vtt, .md, .po, .html, .svg) may be UTF-8, UTF-16 with a byte-order mark, or a legacy Windows code page; HTML, SVG and PO files may also declare another common charset. A non-UTF-8 file that declares no charset (also .csv/.tsv, .ini and the other text formats) is read in the code page of the project's SOURCE language (Greek Windows-1253, Russian Windows-1251, Central European Windows-1250, Japanese Shift_JIS, Chinese GBK or Big5, Korean 949, Western languages Windows-1252, and so on), and the upload warns (file_warnings kind text_encoding) when the decoded letters look wrong; documents uploaded before this rule keep their import encoding. A non-UTF-8 file is converted on upload. On export a translated plain text, subtitle, HTML, CSV/TSV or INI file goes back in its own code page when every translated character fits, else as UTF-8 under UTF-8 declarations; .md and .svg files and every translated PO are UTF-8 (formats with their own encoding rule, such as .properties, keep it). A file that cannot be read as any of these (bytes undefined in Windows-1252, or a binary file) is refused with 're-save the file as UTF-8' (HTTP 422 on the API, the same text on web, CLI and MCP)."
  - "OpenDocument files (.odt and .ott text, .ods and .ots spreadsheets, .odp and .otp presentations, .odg and .otg drawings) are translated paragraph by paragraph: body text, headings, lists, tables, footnotes and endnotes, text boxes, header and footer text, spreadsheet text cells (formulas, numbers and dates are left alone), slide text and speaker notes. Bold, italic and links are kept as inline tags; fields, bookmarks and images stay in place. Tracked deletions, slide masters, sheet names and image alt text are not translated; comments (annotations) are translated only when the project's 'Translate comments' option is on. The export keeps the file type and declares the target language. Password-protected files are refused (save a copy without a password first)."
  - "Server-page templates (PHP .php/.phtml, JSP .jsp/.jspf, ASP.NET .aspx/.ascx, ERB .erb, server-side include .shtml/.shtm/.stm) are translated like HTML. Code blocks (<?php ?>, <?= ?>, <% %>, <%= %>, <%@ %>, <%-- --%>, JSP ${...}, <!--#... -->) are never translated or run and come back byte for byte: an output expression inside a sentence is a protected placeholder (dropped by a translation, it is put back at the end of the sentence), any other code block splits the text, and an attribute whose value holds code is left alone. A file whose code cannot be separated safely (an unclosed block, code used as a tag or attribute name, code that prints half a tag) is refused with the line number. A .php file is read as a page template unless it is a PHP language array; a .php file that is PHP code with no page text is refused. Razor .cshtml is not covered yet."
  - "PHP localization arrays (.php: Laravel lang files `return ['key' => 'value']` with nesting and array(), CodeIgniter `$lang['key'] = '...';`) are documents: every string value becomes a segment, keys stay. The file is tokenised, never executed: anything that is not a static literal (a function call such as __() or env(), a constant, a variable or {$x} interpolated into a string, namespace/use, HTML after ?>) refuses the file with a line number. Laravel :placeholders, pluralisation conditions ({0}, [1,*]) and the | separator, printf (%s, %1$s), simple ICU arguments ({0}) and HTML tags are protected tokens. The export rewrites only translated strings, in the same quote style (a translated concatenation or heredoc becomes one quoted string)."
  - "AsciiDoc (.adoc, .asciidoc, .asc): paragraphs, section and block titles, list items, description lists, admonitions and table cells are translated. Listing, literal, passthrough and comment blocks, source-styled and indented literal paragraphs, line comments, attribute entries and the header's author and revision lines stay as they are. include:: and other preprocessor lines are kept and never followed. Attribute references such as {name}, inline macros (link:, xref:, image:, kbd:), monospace code and formatting marks are protected tags; link and footnote text is translated inside its tag. The exported file declares the target language with :lang:. CSV and DSV tables are not translated; an OpenPGP .asc file is refused (HTTP 422)."
  - "EPUB 2 and 3 (.epub): the book title and description, every XHTML chapter in reading (spine) order, and the navigation and NCX table-of-contents labels are translated; CSS, fonts and images are copied untouched, and export declares the target language in the package and each chapter. A DRM-encrypted EPUB is refused (font obfuscation is fine). SVG chapters are not translated."
  - "A MadCap Flare project (.flprjzip; a .zip of the project folder renamed to .flprjzip also works) is ONE document: topic and snippet text, .flvar variable definitions, .fltoc TOC titles, .flglo glossary terms and definitions and index keywords become segments; MadCap elements are protected inline tags and a variable inside a topic is never translated; conditions, attributes and every other file are kept byte for byte and the export is the same zip layout. A zip that is not a Flare project, or has unsafe paths, symbolic links, duplicate paths or XML entity declarations, is refused with a plain reason."
  - "CSV/TSV and spreadsheets by column (Batch 6): a .csv/.tsv file is a document. A column mapping says which column is the source, which column each target language is written into, and which columns are shown to the translator as the segment note: `source=English, target.de=German, target.fr=fr, key=id, context=notes, maxlen=limit` (header names or 1-based column numbers; also `header=yes|no|auto` and, for CSV, `delimiter=comma|semicolon|tab|pipe`). Web: the project page upload form, Spreadsheet columns. CLI: `doc upload <project_id> <file> --columns \"...\"`. API: POST /api/documents form field `columns`. A CSV/TSV without a mapping is read from its header row (`source`/`text` or the source language code is the source; `target`/`translation` or a target language code such as `de` or `fr-FR` is that language's column; `key`/`id`, `context`/`notes`, `max length` become the note); with no such header every text cell is translated where it stands. An XLSX is column-mapped only when a mapping is given (otherwise every text cell is translated in place, as before). A multilingual sheet (one column per language) exports one file per target language, each with only its own column filled; a target cell that already holds text keeps it while its segment is untranslated. Columns and rows the mapping does not touch keep their exact bytes (CSV) or values (XLSX); the delimiter, quoting, line endings and encoding are kept (UTF-8 with or without BOM, UTF-16 with BOM; a Windows-1252 file is exported as UTF-8 with a BOM). Formula cells (`=SUM(A1)`, Excel's `=\"0012\"`) are never translated, and every cell the export writes that starts with = + - @ (or TAB/CR) is prefixed with an apostrophe so a spreadsheet cannot run it as a formula. A mapping that does not fit the file (unknown column, no source) is refused with a plain message (HTTP 422 on the API)."
  - "Spreadsheet glossaries and TMs: a glossary import also takes .xlsx and .tsv (header `source_term,target_term,...`, or `source`/`target`, or the two language codes; no header means source then target), and a TM import also takes .xlsx, .csv and .tsv with two columns (source, target). Both are converted to the CSV/TMX the importers already read, so every import rule (dedupe, chunked writes, the integrity gate, locale matching) is the same. Web: the project page import forms. CLI: `glossary import`, `tm import`. API: the same import endpoints."
  - "Freedesktop desktop entries (.desktop launchers): the unlocalized Name, GenericName, Comment and Keywords values of [Desktop Entry] and every [Desktop Action] group are translated (each Keywords item on its own); Exec, Icon, Categories, other groups, comments and other locales' lines are never touched. The exported file keeps the source lines and adds Name[fr_FR]=... (POSIX locale form; sr-Latn becomes sr@latin, zh-Hans zh_CN) right after each source key, or replaces that locale's existing line. The spec's backslash escapes (space, newline, tab, return, backslash, and semicolon inside Keywords) are read and written. UTF-8 only."
  - "Haiku catalogs (.catkeys): the translation column of each entry is filled, the source string is the segment; source, context, comment and untouched lines stay byte for byte. Export sets the header language to the target's English name (german, portuguese (brazil)) and keeps the fingerprint (Haiku computes it from the source strings, which never change). Name the exported file after the locale (de.catkeys). Entries with no letters (symbols, digits) are not segments."
  - "Microsoft HTML Help (.hhc table of contents, .hhk index, .hhp project): in .hhc/.hhk only the Name and Keyword values of each text/sitemap entry are translated (in an index, the keyword and the topic titles that follow it); Local, URL, ImageNumber, Merge and every other byte are kept. A See Also reference follows the translation of the keyword it names. In .hhp, Title= and the window captions are translated and Language= is set to the target language (LCID). These files are read in their Windows ANSI code page (Windows-1252, or a charset the file declares) and exported in the TARGET language's ANSI code page (Russian Windows-1251, Japanese Shift-JIS, ...), because HTML Help 1.x shows its Contents and Index panes in that code page; a translation with characters that code page cannot hold is refused with a message naming the character. The operator can set HTMLHELP_UTF8_FALLBACK=1 (environment, restart) to write UTF-8 instead, with a logged warning (HTML Help Workshop will not show those characters correctly). A file that is already UTF-8 or UTF-16 stays in that encoding."
  - "Wiki markup: MediaWiki (.wiki, .mediawiki, .wikitext) and DokuWiki (.dokuwiki). A DokuWiki page file is .txt on disk, which uploads as plain text, so rename it to .dokuwiki first. Headings, paragraphs, list items, table cells and link labels (and MediaWiki file captions, DokuWiki image captions and footnotes) are translated. Link targets, templates and parser functions {{...}}, <nowiki>, <pre>, <code>, <syntaxhighlight> and similar tags, %%...%% and <code>/<file> blocks (DokuWiki), comments, magic words such as __NOTOC__, signatures, categories, #REDIRECT lines and space-indented preformatted lines stay as they are. Template parameters are translated only when the install lists them in the WIKI_TEMPLATE_PARAMS setting (Template:param pairs, for example Quote:text,Note:1). Neither wiki declares a page language in the page source, so nothing is stamped on export."
  - "PowerPoint files (.pptx, and the .pptm, .potx, .potm, .ppsx and .ppsm variants) are translated slide by slide: text boxes, tables, grouped shapes, SmartArt, chart titles, speaker notes (marked notes) and hidden slides (marked hidden), then picture and shape alt text. Slide layouts and masters and chart data labels are not translated; comments (classic and modern, with replies) are translated only when the project's 'Translate comments' option is on. Office macro and template files (.docm, .dotx, .dotm, .xlsm, .xltx, .xltm, .pptm, .potx and so on) are accepted wherever .docx, .xlsx and .pptx are; the exported file keeps its macros byte for byte and its file type, so a macro file never turns into a macro-free one. A file WITH macros under a macro-free name (.docx, .xlsx, .pptx, .dotx, .xltx, .potx, .ppsx) is refused (rename it .docm, .xlsm, .pptm and so on); the Microsoft 365 connector skips it with the same reason. Legacy binary .doc, .xls and .ppt are not accepted (save them in the newer format first)."
  - "Subtitles: .srt, .vtt, YouTube .sbv, and .sub as SubViewer 2.0 or MicroDVD (told apart by content). Only cue text is translated; timecodes, frame numbers, headers and MicroDVD style codes such as {y:i} (kept as protected tags) are unchanged, and a line break becomes [br] (SubViewer) or | (MicroDVD). A .sub that looks like both formats, SubViewer 1.0, or a binary VobSub image subtitle is refused with a plain reason (HTTP 422)."
  - "XML, DITA and DocBook (.xml, .dita, .ditamap, .bookmap, .dbk) translate in place by W3C ITS 2.0 rules: element text is translatable, attributes are not unless a rule says so, its:translate, its:withinText (inline tags become tokens; 'nested' elements such as footnotes and index terms are their own segments), its:locNote (shown as the unit note) and xml:space='preserve' are honoured, and <its:rules> written inside the file apply. DITA and DocBook (4.5 and 5) are recognised from the DOCTYPE or root element and use bundled rule sets: code (codeph, codeblock, programlisting, screen, filename and similar), draft-comment, remark, conref/conkeyref elements and translate='no' stay untranslated; DITA navtitle, map title and image alt attributes translate. Every untranslated byte is kept (DOCTYPE line, comments, attribute quoting); the export declares the target language on the root (xml:lang, or lang for DocBook 4.x). The DOCTYPE is never resolved: a DTD internal subset is refused and entities such as &product; stay as protected tokens. A DITA map is one file; topics it references are uploaded separately (zipped DITA projects come later). A separate rules file per project is not configurable yet."
  - "Mozilla localization files: .dtd entity files and Fluent .ftl files upload and export like any document (UTF-8 only; a non-UTF-8 file is refused with 're-save the file as UTF-8'). DTD: each general entity value is one unit; entity names, parameter entities, external entities and comments are never touched, and nothing is expanded or fetched. Fluent: message values and attributes are units, each select-expression variant ([one], *[other]) is its own unit, placeables such as { $name } and { -brand-name } are kept as written, and terms (-brand-name) are never translated unless the server sets FTL_TRANSLATE_TERMS=1. Mozilla-style .properties (UTF-8, LOCALIZATION NOTE comments, %S placeholders) are read by the .properties filter and their translations are written as UTF-8 text."
  - "Salesforce Translation Workbench files (.stf: Source, Outdated and untranslated, Bilingual): the LABEL column is translated, keys are never changed, and the export is the file Translation Workbench Import expects (Bilingual TRANSLATED rows get the TRANSLATION column, every other row gets the translation in place of LABEL; Language code is set to the target). Escapes (\\n, \\t), {0} arguments and {!merge} fields are kept. STF has no length column; Salesforce label limits by key type (field label 40, custom label 1000, picklist value 255, help text 510) are reported, never truncated."
  - "Trados TagEditor .ttx files (Trados 2007 and earlier) upload like any document and come back as TTX. Only a pre-segmented TTX can be translated: each <Tu> segment is one unit. The original document's tags (<ut>) are protected tags. A segment that already has a translation is kept and never overwritten; untranslated segments stay empty. Written segments get MatchPercent 0 and Origin mt. The file keeps its encoding (usually UTF-16) and every other byte."

Locked segments (gs4tr:locked or TXML locked=true), and segments whose target the translator already confirmed (TXLF: a target state past needs-*; TXML: a target that is not raw MT or a fuzzy match under 100), are never overwritten; untranslated segments stay empty; every other byte of the file is kept. TXML localizable blocks and revision history are left as they are."
  - "Bilingual CAT files: Trados .sdlxliff/.sdlxlf, memoQ .mqxliff and Phrase .mxliff upload like any document and come back in the same format for the vendor tool.   - "Trados Studio packages: upload a project package (.sdlppx) to a project and it becomes one document per target-language SDLXLIFF file the project translates into; source files, translation memories, reports and files in other languages are skipped and listed on the project page.   - "Multilingual XML (.xml files holding the same text in several languages as sibling nodes) is recognised automatically: siblings with xml:lang or lang (<text xml:lang='en'>..</text><text xml:lang='de'>..</text>) or elements named by language (<item><en>..</en><fr>..</fr></item>), when at least two groups hold two or more languages. Segments are the source-language nodes (child elements are inline tags). Each target-language export writes the translation into that language's sibling (an existing one is replaced, a missing one is created after the group with the source's indentation, its language attribute or element name switched and id/xml:id dropped); every other language and byte is kept.   - "Broadcast captions: Scenarist SCC (.scc, CEA-608 closed captions) and EBU STL (.stl, Tech 3264 binary subtitles). ## What this is for

This is where the actual work lives. Everything else in the app - workflows,
glossaries, memory, engines - exists to make what happens to a document better.

## The normal path

1. **Upload** the file into a project that has your target languages.
2. **Apply 100% TM matches** first. It is free and it removes work.
3. **Translate**, or better, **run a workflow** so the checks happen too.
4. **Review** whatever is flagged. The editor shows you source, target, TM
   suggestions and the exact QA finding side by side.
5. **Approve** the segments you are happy with - that writes them to memory.
6. **Export** the file, or export the whole project as a delivery bundle.

## Reading the review queue

Do not read "2/2 translated" as "done". A segment can be fully translated and still
held for review because a check found something. The detailed view is what tells you
how many, and why - it names each family carrying a flag, e.g.
`5 flagged for review (glossary 3, tag_integrity 2)`.

## Current warts worth knowing

- If segments come back in English with a "substituted" warning, the export guard
  caught damaged formatting and shipped the source instead of a broken file. That is
  it working, not failing.
- Tag damage is treated conservatively: any divergence, including a reorder that
  keeps every token, counts as damage and blocks export. The per-paragraph and
  per-segment repair tools are the mitigation.
- `doc translate` from the CLI runs synchronously in your terminal, while the web
  button enqueues a background job. Same result, very different waiting.
