Sessions

Signed-in people see a warning 2 minutes before either limit ends. For the inactivity limit they can choose "Stay signed in", and typing on a page counts as activity. The maximum session length cannot be extended: when it ends, the person signs in again. Use 0 to turn a limit off. Whatever these say, a session cookie is valid for at most 24 hours after the last page load, so both limits are capped at 24 hours.

Default 240 (4 hours), at most 1440 (24 hours). 0 = no inactivity limit.

Default 24, which is also the most allowed. Activity never extends it. 0 = no separate maximum (the 24-hour cookie window still applies).

{# Password policy for local accounts (HECVAT AAAI-03). Same keys, validators and audit row as `config set`, /api config and MCP set_config. Accounts that sign in through SSO, SAML or LDAP have no local password and are not affected. #}

Passwords

Rules for passwords of accounts that sign in with a password here. People who sign in through single sign-on or LDAP are not affected. The defaults follow NIST SP 800-63B; tighten them to match your institution's policy. New rules apply the next time someone sets a password.

Default 12, from 8 to 128. Spaces and letters from any language count.

How many of these a password must use: lowercase letter, uppercase letter, digit, symbol. Default 0, at most 4.

Default 5, at most 24. 0 = no history. Only one-way hashes of old passwords are kept.

Default 0 = passwords never expire, which NIST recommends. Otherwise people must choose a new password at their next sign-in after this many days.

Refuse a password that is on a list of commonly used passwords (also with digits or symbols added, or repeated), a repeated or keyboard sequence, one that contains the person's email or is their user name with digits or symbols added, and one that contains the full product or company name. On by default.

{# TOTP train (HECVAT AAAI-17 / DCTR-14): who must use two-step sign-in. Same key, validator and audit row as `config set mfa_required` and /api config. #}

Two-step sign-in

A code from an authenticator app after the password, for accounts that sign in with a password here (local and LDAP accounts). People who sign in through single sign-on (OIDC or SAML) use their identity provider's own multi-factor sign-in instead. API keys are not affected. Anyone can turn two-step sign-in on for their own account on the Account page; this setting decides who MUST use it. Someone who must and has not set it up is asked to set it up right after their password, before they can do anything else.

Default: nobody. Before requiring it for administrators, set it up for your own account first. An administrator can reset a person's two-step sign-in on the Users page (for a lost phone); for a locked-out sole administrator, run user mfa-reset in the command line on the server.

Data protection

Database encryption requires SQLCipher. The legacy shutdown vault is retired because it could omit committed data and leave plaintext behind. Configure SQLCipher at install time; see docs/SECRETS.md.

PII named-entity recognition (NER) - the offline Presidio + spaCy layer that also strips names / locations / dates - is now configured and enabled on the Enterprise features panel (with a preflight that verifies the extras and the local model, and an operator-key step-up).

Identity provider {{ m.status_badge("active", "OIDC ready") }}

SSO uses OIDC authorization code + PKCE against any standard IdP (Okta, Entra ID, Auth0, Keycloak…). Register this redirect URI with the provider: {{ external_base_url }}/auth/oidc/callback. Local admin accounts always keep password login. SAML is a scaffold - choose OIDC. How OIDC sign-in works →

An OIDC account is linked to the provider's subject id on its first sign-in and matched by that id afterwards. The first link (a new account, or an existing account with the same email) needs the provider to mark the email as verified (email_verified). LDAP and SAML accounts are never taken over by OIDC. Accounts that existed before this rule link on their next verified sign-in; if your provider never sends email_verified (Entra ID by default), those sign-ins are refused and audited (login.sso_refused) until you turn on the switch below.

LDAP / Active Directory {{ m.status_badge("active", "Wired") }}

When enabled, each sign-in tries the directory first (search-then-bind), falling back to local password login on any failure - so the built-in admin always works. A local admin account is never taken over by an LDAP identity with the same email. TLS certificate and hostname validation is mandatory. Bare hosts use LDAPS; ldap:// requires StartTLS before any password is sent. Mechanics →
