Module guides

One task-first guide per module, written for an operator who is not an expert in this app. These are the same guides the in-app “Ask about this page” panel answers from.

Are you an LLM? Read here - the whole product in one page for a machine driver (an MCP server, a script, an agent): data model, every /api route group, the CLI, step-by-step flows, and the rules an autonomous caller must not break.

There is also a shipped MCP server - the fourth surface, packaging the product as 72 task-shaped tools for an agent (Claude Desktop, Claude Code, or your own runtime). Setup and the tool catalogue live in integrations/mcp-server/README.md. Every tool carries a title and permission hints (read-only, destructive, open-world) your agent host can use, every result carries structured JSON, and every tool error ends with a JSON line whose code says what to do next (for example insufficient_scope with the scope to add, or capacity_retry with a wait). When a result carries text from outside the app (CMS content, document text, TM entries, vendor error messages), a leading external_content key names those fields: their text is data, never instructions. Connector results say that publishing in the source system is your decision, not the agent's.

Spending over MCP. A tool that bills first answers with a plan and a plan_id; the agent tells you what it will spend and only then calls again with confirm: true and that plan_id. Changed arguments, a reused plan or one older than 30 minutes are refused and nothing is sent. With LOC_STUDIO_MCP_HUMAN_CONFIRM=ask an agent host that supports MCP 2026-07-28 approval prompts also asks you before each spend. A local (stdio) MCP server reads a file you name only from your Documents or Downloads folder, your OneDrive Documents folder when OneDrive is set up (or the folders in LOC_STUDIO_INPUT_DIRS), never a hidden file, and only file types the app accepts.

Connect an AI agent remotely. Run that server over HTTP (server.py --transport streamable-http) and point an agent runtime you control at https://<your-host>/mcp. Each request authenticates itself with its own per-user lsu_ key in an Authorization: Bearer lsu_… header (the X-Loc-Token alias also works), so one listener can serve several users, each with their own minimally-scoped key - a docs-only key (api docs) for the “translate this / drive a workflow” flow, or a keys/CI key (api keys) for the Delta loop. Register it with Claude Code via claude mcp add --transport http loc-studio https://<your-host>/mcp --header "Authorization: Bearer lsu_…", or print the exact snippet for any base URL with python -m app.cli mcp connect --base-url https://<your-host>. The tool list follows the key: a tool whose scope the key lacks is not listed. To load fewer tools, set LOC_STUDIO_MCP_TOOLSETS (for example orientation,connectors) or add ?toolsets=keys to the URL (mcp connect --toolsets prints it); the names are the tool families plus connectors and admin. Unless MCP OAuth is switched on (below), the listener does no sign-in of its own, and either way it serves plain HTTP, so run it behind TLS you control (your own proxy). Behind that TLS this is the server half of a claude.ai static-bearer connector (it reads the Authorization: Bearer header claude.ai’s custom-headers field sends), but claude.ai’s request-header auth is a gated beta with a known open bug (anthropics/claude-ai-mcp#644), so it is not confirmed working from claude.ai yet. Full detail and the failure signature: the remote section of integrations/mcp-server/README.md.

Connect by signing in (MCP OAuth, off by default). An administrator can make this install the OAuth sign-in server for its MCP server (Security > MCP OAuth, or config set mcp_oauth_enabled 1 plus mcp_oauth_resource and python -m app.cli mcp-oauth rs-secret), then start the listener with LOC_STUDIO_MCP_OAUTH_RESOURCE, LOC_STUDIO_MCP_OAUTH_ISSUER and LOC_STUDIO_MCP_RS_SECRET. Apps such as claude.ai or ChatGPT connectors then connect with your normal sign-in and a consent page that shows the app and where your answer goes; you choose documents and keys access, and administration is never included. Your connected apps are listed, and can be disconnected, on Account > Connected apps (GET /api/mcp-oauth/grants, mcp-oauth grants). Personal API keys keep working as before.

New MCP sessions are admitted at a shared default of 10 at once, then one per minute. An administrator can give a specific API key its own budget: set LOC_STUDIO_MCP_CLIENT_LIMITS in the listener’s environment and restart it, and print the entry for a key with python -m app.cli mcp client-limit --key-env VAR --burst N --refill-per-minute N. Unlisted keys keep the shared default.

Slow MCP actions (a connector sync, term extraction, an image translation) start in the background and wait up to 45 seconds. If the work is still going, the tool answers with a job number; job_status then shows its progress and, once finished, its result (how many items were created or updated, held back for review, or failed). A timeout no longer means the work stopped: check the job before running the action again. Every spending tool also takes an optional idempotency_key, and the API takes the matching Idempotency-Key and Prefer: respond-async headers, so a call that is sent twice runs once.

Overview

A local, MT-first Translation Management System. Nearly all content is translated automatically by configurable multi-agent LLM workflows; the built-in CAT editor is for the exception slice that needs human post-editing. It runs entirely on your machine and can run fully air-gapped against local models.

Pipeline: upload → parse/segment → TM & glossary leverage → MT workflow → LQA → post-edit → export. With no key, translation is refused rather than faked. To try everything offline, choose Mock in Setup AI (or run config set default_provider mock): it returns clearly labelled placeholder text and a MOCK banner shows on every page. Add a provider (cloud key or a local server) to go live.

Accessibility

Our target is the Web Content Accessibility Guidelines (WCAG) 2.2 at level AA for the web interface. This section says what works today, how to use it with a keyboard or a screen reader, and the gaps we know about.

Keyboard

Everything in the web interface can be used with a keyboard. The first Tab on every page reaches Skip to content, which jumps past the navigation to the page itself. Every link, button and field shows a visible focus ring when it has keyboard focus, also in Windows High Contrast (forced colors) mode, and the page scrolls so the focused control is not hidden under the top bar or the Editor toolbar.

Keyboard shortcuts

No shortcut uses a single letter key outside an open menu, so nothing fires while you type in a field. These are all the shortcuts there are:

  • Anywhere outside a text field: Ctrl+K (Cmd+K on a Mac) opens the navigation palette: type to filter, use arrows and Enter to open, or Escape to close and return focus. Its search row submits the existing top-bar search.
  • Editor, in a translation box: Enter saves and moves to the next segment; Shift+Enter starts a new line; Ctrl+Enter (Cmd+Enter on a Mac) approves the segment and moves to the next unconfirmed one; Alt+A (Ctrl+Shift+A on a Mac) opens the alternate translations for that row, also with VoiceOver on (the Mac shortcut does not use Option, so it never types a letter and is not a VoiceOver command). The same key also works from the row’s other buttons, and the row’s alt button (read as “alt for segment” and the segment number) does the same with a click. Moving into or out of a box without changing its text never changes the segment’s status: only a change to the text makes it edited, and an approved segment stays approved until its text is changed. When an approved target dropped or added a placeholder, a dialog asks whether to save it to TM anyway; Escape or Do not save to TM keeps it out of TM.
  • Editor, alternate translations list: Up and Down arrows move through the choices, Home and End jump to the first and last, Enter inserts the chosen text and saves it, and Escape or Alt+A closes the list and returns you to the translation box.
  • Editor, concordance search box: Enter searches.
  • User menu (your name or initial, top right): Enter or Space opens it and moves to the first item; Up and Down move, Home and End jump to the first and last, typing a letter jumps to the next item that starts with it, and Escape closes it and returns focus to the menu button.
  • Navigation menu on narrow windows (below 900 pixels wide, the sidebar opens from the menu button in the top bar): Tab stays inside the menu while it is open, and Escape closes it and returns focus to the menu button.
  • Sidebar layout (windows wider than 900 pixels): choose the Edit sidebar layout button below New project in the sidebar. Each link and group then has Move up and Move down buttons, and the width has Narrower, Wider and Reset width buttons. In this mode the sidebar’s edge is also a keyboard control: Left and Right arrows change the width by 20 pixels, Home and End set the narrowest and widest, and Enter resets it. Choose Done to finish.
  • New workflow, building aids tabs: Left and Right arrows move between tabs, Home and End jump to the first and last.
  • Workflow diagram: dragging a step is optional. The move up and move down buttons in the step list always reorder steps, and Escape cancels a drag in progress.
  • Dialogs: Escape closes the New project dialog. The sign-out warning (below) cannot be dismissed with Escape, because its countdown keeps running; choose one of its buttons instead. Once a session has ended, the “You have been signed out” message cannot be dismissed either; choose Sign in again.
  • Page layout: while you arrange a page (the Edit layout button, on every page that has one), Escape cancels editing and keeps the saved arrangement.
  • Waiting for a page: after you submit a form, Escape stops waiting and makes the form’s buttons usable again.

Zoom and reflow

Pages can be zoomed to 200% and read normally. At 400% zoom (a window 320 CSS pixels wide) pages reflow into a single column, and below 900 pixels the sidebar moves behind the menu button in the top bar. Data tables keep their columns and scroll sideways inside their own box instead; each such box can be reached with Tab and scrolled with the arrow keys. Apart from those tables, pages do not scroll sideways. This is checked automatically on the sign-in page, Dashboard, Projects, a project, the Editor, the Run view, workflows, a glossary, queries, users, settings, a customer and this Help page; other pages use the same layout rules.

Themes and motion

  • Light, dark or match my computer: the account menu (your avatar at the top right) and My account › Appearance both offer Light, Dark and Match my computer. Your choice is saved with your account, so it follows you to every browser; Match my computer follows your operating system, including when it changes.
  • Get started: the setup checklist for new administrators and linguists is in the account menu until you dismiss it. Once dismissed, turn it back on under My account › Appearance › Get started.
  • Reduced motion: when your operating system asks for reduced motion, animations and transitions stop: the pulsing “running” marker becomes a still dot and busy indicators stop spinning. Without that setting the pulse still stops after a few seconds.
  • Interface language: English, German, Spanish or French, under My account › Language.

Screen readers

Every signed-in page has a main navigation landmark, a banner with the top bar, a main landmark and one top-level heading, with section headings below it. Source and target text carry their own language (and right-to-left direction for languages such as Arabic and Hebrew), so a screen reader can read each in the right voice. With the German, Spanish or French interface, most page text is still English, so a page is declared English unless all of its text is translated (today only the sign-in page is); the translated parts (the sidebar, the top bar, banners, the sign-out warning, busy messages and translated headings and labels) are marked with the interface language, and error messages, which are English only, are marked as English. Workflow diagrams are described in text: in the workflow builder by the step list, and on the Run view and a drafted workflow’s review page by a Diagram as text list of each step, its role and engine, and where a pass or a failure goes.

Changes that happen without a page load are announced:

  • Editor: a saved segment, an approval, a save or approval that failed, an inserted alternate or translation memory match, and repaired formatting tags.
  • Run view: the run starting, each step, progress at 25, 50 and 75 percent, completion, a pause for human review, cancellation, failures and a lost connection. Bursts are combined into one summary instead of a stream of messages.
  • Buttons that take a while say that they are working and when they finish, and the sidebar layout controls say the new position or width.
  • Sign-out warning: announced when it opens, then at 60 and 30 seconds (the visible countdown itself is not read aloud every second).

Forms and errors

Every field and button has a label that a screen reader reads. Choosing an option in a list never submits a form on its own; there is always a button. When a form cannot be saved, the error appears at the top of the page (inside the dialog, for the New project dialog), receives focus so a screen reader reads it, and starts the page title with “Error:”. When the error is about one field or section, it links there, and that field is marked as invalid.

Signing out after inactivity

When sign-in is required, two limits end a session. The administrator sets both on the Security page: an inactivity limit (by default 4 hours; typing on a page counts as activity) and a maximum session length counted from sign-in (by default 24 hours, which is also the most allowed; activity never extends it). Two minutes before either limit ends, a warning with a countdown appears. For the inactivity limit, Stay signed in has focus and extends the session. The maximum length cannot be extended, so then Sign out now has focus and you sign in again when it ends. Text you had not saved is kept for that browser tab and offered back (Restore or Discard) after you sign in again. Details are under Session limits and the sign-out warning.

Known issues

  • A review with screen readers (NVDA on Windows and VoiceOver on a Mac) by a person is still pending. Automated checks run on the pages listed under Zoom and reflow.
  • With the German, Spanish or French interface, a translated page title, a translated hint inside a field (placeholder text or a tooltip), and the page layout editing controls on a page that is otherwise English are read with the English voice (WCAG 3.1.2).

Projects & documents

Customer → Project → Document. A project has a source locale, target locales, a default engine, an optional due date and content type, and belongs to an optional customer. Documents are uploaded files ingested in one of two modes:

  • Segmented - split into sentence-level units that align with TM (the atomic translation unit; carries source, target, status, TM %, QA flags, Time-to-Edit).
  • Full-text - the whole document is one unit sent to the LLM, no parse/reassemble cycle. Backed by a full-text TM keyed on content hash.

Arrange a page

Upload safety limits. Oversized files are refused with a reason. DOCX and XLSX packages default to 256 MiB expanded, 10000 parts, and at most 200 times expansion for a part larger than 1 MiB. DOCX allows 50000 paragraphs per document, including empty and table paragraphs (DOCX_MAX_PARAGRAPHS). Every file type stops at 50000 segments per document (MAX_DOCUMENT_SEGMENTS; for XLSX, 50000 text cells), 100000 characters in one line or paragraph (MAX_SEGMENT_CHARS) and 500000 segment rows, segments times target languages (MAX_DOCUMENT_ROWS); split a refused file into smaller ones. The same limits apply to connector pulls (a record or run over a limit is refused with the reason on the run, before any translation), adding a target language to a document (the language is skipped with a notice on the document), key-file imports, evaluation datasets and vendor XLIFF returns. TMX, TBX and glossary imports stop at 500000 entries (MAX_DOCUMENT_ROWS) and import nothing. One connector run may fetch at most 50000000 characters of source records (CONNECTOR_RUN_CHAR_BUDGET); a larger run is refused whole with the reason on the run, so lower the connection's record limit or narrow its scope. XLSX now allows up to 500000 cells, enough for a 20000 by 14 catalog, across worksheet rectangles and cumulative cell, merge, hyperlink, comment and table work; the rectangle bound remains because empty cells also consume memory. It allows 100000 rows per sheet, and 32767 characters per cell. Split a refused workbook into smaller files. Workbooks also default to about 8.4 million total text characters, counting repeated values and formulas, to prevent a small file from expanding into a huge document. PDFs default to 1000 pages; scanned pages are scaled to at most 4000 pixels per edge for OCR, with at most 2.5 billion rendered pixels per document (PDF_OCR_MAX_TOTAL_PIXELS). Over-budget PDFs are refused before any rendering. Administrators can configure these limits. They also apply to API, CLI and MCP uploads and to reopening Office files for export. If upload capacity is busy, retry shortly. Remote clients receive HTTP 413 for size limits or retryable 503 for busy workers. Sign-in and anonymous request bodies default to 1 MiB; signed-in requests allow the upload cap encoded as base64 plus 1 MiB of envelope space.

On a wide screen, the Edit layout button at the top right of a page header lets you arrange the cards below it: stack them, or put two or three side by side, like the Translation memory and Glossary cards of a project. Drag a card, or use the Move up, Move down, Move left, Move right and Own row buttons on each card, and pick each row's width (1 wide, 2 across or 3 across). Done saves, Cancel or Escape puts things back, and Reset to default returns to the standard order. The layout is yours: it follows your account to any computer and applies to every page of that kind (every project page, every connection page), and nobody else's page changes. The page header and any warning or notice above the cards always stay on top; on a project page that includes the missing-customer warning, the Keys card and the download card. Reports is the exception: its pinned note, Target languages chart and Report builder stay below the charts.

Pages you can arrange: Project page, Dashboard, Connectors, Connector catalog, Connector type page, Connection page, Setup AI, Users, Settings, Security, Account, Content routing, Document page, Reports, My work, Customer page, Glossary page, Style guide page, Vendor page, Multilingual workflow page, Building blocks and Queries. Pages whose order is a sequence you work through (the Editor, a run, the workflow builder, numbered setup steps) keep their order. Headless: layout list names every page key, then layout show <page>, layout set <page> --rows ... and layout reset <page>, or /api/account/layouts.

Search

The search box at the top of every page, and Ctrl+K, open one search dialog. Click the box or start typing and it shows the pages that match plus live results as you type; Enter opens the full results page at /search, grouped into Projects, Documents, Translation memory, Glossary terms, Workflows and Connections, each with a count. It searches project and customer names, document file names, translation memory source and target text, glossary terms, workflow names (archived workflows are left out) and connection names or connector types. It does not search inside documents and never looks at connection credentials or settings. You only ever see what you can already open: projects you are not a member of, other customers' memory, glossaries, workflows and connections, and anything hidden from your role are neither listed nor counted. Queries are 2 to 100 characters, each group shows at most 25 hits per page, counts stop at 1000, and the translation memory search covers the newest 100,000 entries you can open. Headless: search <text>, GET /api/search, or the MCP search_workspace tool.

Supported formats

Every format flows through the same parse → translate → rebuild round-trip, so TM, glossary, workflows, the editor, LQA and export all work identically across them:

  • DOCX - Word, formatting preserved. A document saved as Strict Open XML is read and comes back as Strict Open XML (PowerPoint .pptx too). Text inside nested smart tags, hyperlinks inside tracked insertions and inline content controls translates for documents uploaded after this change; re-import an older document to pick it up.
  • PDF - digital text layer, or vision OCR for scans (renders each page to the project's engine - any vision-capable model, including a local Qwen3-VL; no Tesseract/system binaries, so OCR works air-gapped).
  • HTML (.html/.htm/.xhtml) - translates text between tags with full inline-tag fidelity; markup, scripts and styles are untouched and reassembled exactly.
  • JSON - i18n resource files; only string values translate.
  • Markdown (.md) - prose translates; headings, lists and fenced code preserved.
  • Wiki markup (.wiki/.mediawiki/.wikitext for MediaWiki, .dokuwiki for DokuWiki) - headings, paragraphs, lists, table cells and link labels translate; link targets, templates, code and nowiki blocks, magic words and categories preserved.
  • Plain text (.txt).
  • gettext PO (.po/.pot) - msgid → msgstr.
  • Subtitles (.srt/.vtt) - cue text translates; numbering/timecodes kept.
  • XLIFF (.xlf/.xliff, 1.2 & 2.0) - bilingual interchange.
  • XML, DITA, DocBook (.xml, .dita/.ditamap/.bookmap, .dbk) - translated in place by W3C ITS 2.0 rules (its:translate, its:withinText, its:locNote, xml:space, rules inside the file). DITA and DocBook 4.5/5 use bundled rules: code, draft comments, remarks and conref elements stay untranslated. The DOCTYPE is kept and never resolved; a DTD internal subset is refused.
  • Multilingual XML (.xml) - one file with every language as sibling nodes (xml:lang / lang siblings, or elements named <en>, <fr>) is detected automatically; or set the rule with a <?loc-multilingual mode="xpath" source="en" source-xpath="...{lang}..." target-xpath="...{lang}..."?> line before the root element. The source-language nodes are the segments; each target export fills or creates that language's sibling and leaves the other languages untouched.
  • Apple resources (.stringsdict, .xcstrings, .plist, XML or binary) - plural and device variants translate; a String Catalog export adds or replaces only the target language and keeps the others.
  • Software resources (XML) - Android strings.xml and Java XML properties (.xml), .NET RESX/RESW (.resx/.resw), WiX (.wxl) and Qt Linguist (.ts). Only text values translate; non-text entries, the RESX header and schema, comments and every other byte are kept. Android apostrophes and quotes get a backslash on export; save the result under the matching values-xx folder yourself.
  • XLSX (.xlsx) - Excel; string cell values and the text of text boxes and shapes translate; formulas, numbers, dates, every sheet, pictures (EMF/WMF too), charts, comments, data validation and printer settings come back exactly as uploaded (the translation is written into your own file). Text boxes are offered for files imported after this change; re-import an older workbook to translate its text boxes. A workbook saved as Strict Open XML is read and comes back as Strict Open XML. For a right-to-left target every sheet is set right to left (column A on the right), and so is every sheet of an OpenDocument spreadsheet (.ods).
  • Adobe InDesign IDML (.idml) - export the document from InDesign with File > Save As > InDesign Markup (IDML). Every visible story translates, including table cells, footnotes, endnotes and hyperlink text; a sentence styled across bold or italic ranges is one segment with inline tags, and tabs, special characters, index markers, hyperlinks and XML tags are protected. Text under a hidden condition, notes, tracked deletions and stories on non-printing layers or frames are left as they are. Every other part of the package (spreads, styles, images, fonts) comes back byte for byte. Translated text is tagged with the target language when the package already lists that language (InDesign writes its language list into the file). Open the translated file in InDesign to fix overset text. For a right-to-left target (Arabic, Hebrew, Persian, Urdu and the like) every translated paragraph is set right to left with the Adobe World-Ready Paragraph Composer (a single-line composer becomes the World-Ready Single-line Composer); story and table direction and alignment are not changed. For a CJK target, check the composer in InDesign.
  • And more (about 85 formats in all; each one's rules are in the Documents guide linked below): PowerPoint (.pptx and its macro and template forms), OpenDocument text, spreadsheets, presentations and drawings, Visio, EPUB, e-mail (.eml), CSV/TSV, AsciiDoc, reStructuredText, LaTeX, MDX, server-page templates (PHP, JSP, ASP.NET, ERB), XSLT, FrameMaker MIF, QuarkXPress Tags, AutoCAD DXF, Microsoft HTML Help, subtitles and captions (SBV, SubViewer, MicroDVD, SSA/ASS, TTML/DFXP, SCC, EBU STL), software resources (Java and Apple key-value files, INI, RESJSON, YAML, TOML, JSON5, Flutter ARB and other JSON dialects, PHP arrays, JavaScript/TypeScript message modules, Windows .rc, XAML, Mozilla DTD and Fluent, .desktop, Haiku catalogs, Angular XMB/XTB, compiled gettext .mo, Apple .xcloc, Salesforce .stf), CAT bilingual files and packages (Trados SDLXLIFF, .sdlppx/.sdlrpx and TTX, memoQ, Phrase, Wordfast, WorldServer), and raster images for image localization. A .zip upload makes one document per supported file inside it.
  • MadCap Flare project (.flprjzip: Flare's zip project; a .zip of the project folder renamed to .flprjzip also works) - one upload translates topic and snippet text, variable definitions (.flvar), TOC titles (.fltoc), glossary terms and definitions (.flglo) and index keywords. MadCap elements (variables, snippets, conditional text, cross-references, glossary terms, drop-downs) are protected tags; a variable inside a topic is never translated. Conditions, attributes and every other file are kept byte for byte, and the export is the same zip layout. A zip that is not a Flare project, has unsafe paths or links, or declares XML entities is refused.
  • Adobe InCopy ICML (.icml, and WoodWing .wcml articles) - export the story from InCopy or InDesign (File > Export > InCopy Document). The text translates exactly like an IDML story (inline tags, tables, footnotes, hidden conditions left alone); styles, swatches and every story you did not translate come back byte for byte, and the result is an .icml to place or open in InCopy. Right-to-left targets get the same paragraph direction and World-Ready composer as IDML.

Text files (.txt, .srt/.vtt, .md, .po, .html, .svg) may be UTF-8, UTF-16 with a byte-order mark, or a legacy Windows code page; HTML, SVG and PO files may also declare another common charset. A file that is not UTF-8 and declares no charset is read in the Windows code page of the project's source language (Greek Windows-1253, Russian, Ukrainian and Bulgarian Windows-1251, Czech, Polish and other Central European Windows-1250, Turkish Windows-1254, Hebrew Windows-1255, Arabic Windows-1256, Baltic Windows-1257, Vietnamese Windows-1258, Thai Windows-874, Japanese Shift_JIS, Chinese GBK (GB18030 when GBK cannot read it) or Big5, Korean Windows-949, Western languages Windows-1252). A non-UTF-8 file is converted on upload. On export, a translated plain text, subtitle (.srt/.vtt), HTML, CSV/TSV or INI file goes back in its own code page (with its declared charset) when every translated character fits it, and as UTF-8 (declared as UTF-8) when it does not; Markdown and SVG files, and every translated PO file, are exported as UTF-8 (formats with their own encoding rule, such as Java .properties, keep it). A file that cannot be read as any of these (bytes undefined in Windows-1252, or a binary file) is refused with “re-save the file as UTF-8” (HTTP 422 on the API, the same text on web, CLI and MCP).

When the letters of such a file look wrong after decoding (letters of two scripts inside one word, words made mostly of accented letters, or a file that is partly UTF-8), the upload still succeeds with a warning: on the document page, in the upload API response as file_warnings (kind text_encoding), in the MCP submit_translation result, and in CLI doc upload and doc show. If the source language's code page reads the file badly but Windows-1252 reads it cleanly (a Western file in a Greek project), it is read as Windows-1252 and the warning says so. A very short file in a Chinese, Japanese or Korean project can be valid UTF-8 by accident: it stays UTF-8, but warns when its few non-English characters read as Chinese, Japanese or Korean text in the source code page. Check the source segments; if they are garbled, re-save the file as UTF-8 and upload it again. Java .properties files stay ISO-8859-1 (the Java rule) and warn the same way. Documents uploaded before this rule keep the encoding they were imported with.

Untouched files come back exactly as uploaded. When nothing has been translated into a language yet, exporting that language returns your original file byte for byte (no language stamp is added). A translated file keeps the original's byte-order mark and line endings, and the formats above keep their code page when the translation fits it. Accessibility of translated files

DOCX, XLSX and XLIFF exports turn pasted vertical tabs and form feeds into line breaks and remove characters XML cannot store. Saved targets remain unchanged.

PO exports clear fuzzy and previous-string comments on translated entries. Untranslated source fallbacks keep their original comments and translations. When updating the Language header, exports also use the target language's gettext plural rule and number of slots. A translated file declares the target language (the BCP 47 tag of the locale you export, for example es-ES), so a screen reader reads it with the right voice. Image alternative text is translated like any other text. What each format gets, and what it does not:

  • HTML: <html lang> (and xml:lang and a content-language meta tag when the source has them) is set to the target; an Arabic, Hebrew, Persian or Urdu target also gets dir="rtl". Image alt, title and aria-label, and link title and aria-label, become their own segments. An HTML fragment without an <html> element gets no language declaration, and lang attributes on inner elements are left as they are.
  • DOCX: the document default language, styles that used the source language, runs in translated paragraphs and the dc:language property are set to the target (in the East Asian or complex-script slot where that applies).   • PDF: the rebuilt PDF declares the target language and is a tagged PDF (paragraphs in reading order). It is not certified PDF/UA: headings and images from the source are not carried into the rebuilt PDF.
  • Markdown: alt text inside ![...](...) is translated with its line, and the Editor marks those lines. Markdown has no language declaration.
  • XLSX (dc:language), XLIFF (target-language or trgLang) and PO (the header's Language field, when the file has one) declare the target. JSON, plain text and subtitles have no language declaration to set.
  • SVG images (image localization): the plain text of each <title> and <desc> (what a screen reader announces) is translated as its own segment, after the drawing's text; a title with nested markup or inside <metadata> stays as it is. The Delta API

The reason this project type exists. Rather than fetching the whole catalogue and diffing it yourself, you keep a cursor and ask GET /api/projects/{pid}/changes?since= what happened after it. Already holding a full copy and just want what changed since a moment in time? That mode is an incremental filter, not a bootstrap - it never reports deletions and it is since=0, not modified_after, that seeds a fresh catalogue; so keep the cursor feed for the first sync and for tombstones.

Image localization

Upload an image and get it back with its text in another language. The pipeline is detect → translate → re-render, and the middle step is the ordinary document pipeline, so TM, glossary, the refusal guard, LQA and workflows all apply to the text in an image for free.

  • Geometry always comes from a local detector, never from a vision model - pixel coordinates are a measurement, not something to ask an LLM to guess. A vision model is used only to read a low-confidence region's text, and for one context brief per image, both spend-guarded.

With none of them, detection honestly returns zero regions and says so. An embedded fixture sidecar (the deterministic offline path) feeds the mock detector, but only when the resolution above already lands on mock; a real, configured engine is never overridden by uploaded image bytes.
  • Typesetting erases each region with a border-matched fill and fits the translation to the box using bundled fonts. Text that will not fit is flagged as overflow, never truncated - a clipped word is a defect you cannot see in a thumbnail.

Translation

{{ brand }} is MT-first: content is machine-translated by default and only the exceptions reach a human. Every translation is layered:

  • Translation memory - exact (100%) and fuzzy (75–99%) matches are leveraged before an engine call.
  • Glossary auto-attach - the applicable glossary constraints (incl. Do-Not-Translate terms and context-dependent senses) are injected into the prompt for the pair.
  • Refusal guard - a model hedge/refusal is detected, the poisoned output withheld, and the unit routed to needs review instead of being written back to TM (kill-switchable).
  • Output guard (segmented documents) - an agent step whose output repeats its own step instructions or balloons a very short source (a heading number) is withheld and routed to needs review; a dropped or added number keeps the translation but is flagged for needs review (same kill switch as the refusal guard). Full-text documents are not covered.
  • Human-work protection - a segment a person has approved or edited is never overwritten by any later MT, import or vendor return; the write seam refuses and leaves it byte-untouched (core, no kill switch). To re-translate one on purpose, clear its target in the editor (that resets it to new).
  • QE gate: an optional judge (an LLM, or a quality judge such as Jev) scores output and routes low scores to needs review (default OFF). See QE routing gate.
  • Adaptive feedback - approved edits and a doc-context pre-pass feed later segments so the engine adapts within a document.

On the document page every translate button names the language it acts on (for example Translate de-DE (live), Translate de-DE in background and Apply 100% TM matches to de-DE), with a one-line hint under them; Translate all N languages starts one background job per language. A document is new, in translation, in review or done, worked out from its segments in every language. Project counts read “translations (segments x languages)”, because each segment is counted once per target language.

Translate a document with Translate (live) for single-engine MT (segment-by-segment SSE stream; starting it needs the translator role or above), or run a workflow for multi-agent translation. Post-edit the exceptions in the editor (Enter save & next, Ctrl/⌘+Enter approve, Alt+A (Ctrl+Shift+A on Mac) alternates: arrow keys choose, Enter inserts, Esc goes back to the text; approving writes back to TM), run LQA (MQM/DQF typology, score = 100 − Σ penalties, per-pair rulebooks), then Export in the original format.

Repeated segments. Each copy of a repeated source sentence still gets its own machine translation. When you approve one copy, the same text is applied to every other copy in the same document and language that is not yet approved, was not typed by a person, is not TM-locked and is not unlinked. Those copies become Edited with a Propagated badge (never auto-approved, so you still confirm them) and the editor says “Applied to N repeats” and shows an Undo repeats button beside Approve that puts back the copies still exactly as propagated. A copy whose placeholders or inline tags the text would break is left as it was and reported. Use Unlink repeats on a segment to keep a context-specific rendering: it then neither receives nor sends propagated text. Everything is audited as one segment.propagate entry listing the segment ids. Headless: doc approve-segment ID [--no-propagate], doc segment-propagation ID --unlink|--link|--undo, POST /api/segments/{sid}/approve (reply lists propagated and propagation_refused; body {"propagate": false} skips it), POST /api/segments/{sid}/propagation and the MCP approve_segment tool (propagate; propagation = undo, unlink or link manages the repeats instead of approving).

Workflows (multi-agent orchestration)

A workflow is an ordered list of steps you define. Each step is one of:

  • LLM agent (llm_agent) - any role/prompt (translator, in-country reviewer, technical reviewer, finalizer…).
  • LQA (lqa) - structured MQM scoring as a pipeline step. A segment that is only numbers or punctuation (for example 3.) and is identical to its source is correct as it stands, so an “untranslated” or “identical to source” finding on it is shown as advisory (neutral) and does not fail the gate, in segmented LQA, even when the segments are scored as one blob (full-text documents are scored as raw text and keep the finding). Locale-format and number-value findings, and any segment whose number changed, still count in full.
  • Human review (human_review) - pauses the run and hands the document to the editor; resumes on approval. While it waits, the editor shows the pending machine translation read-only under a “Waiting for review on run N” banner that links the run; you approve and resume from the run page, and doc show prints the same wait. Until then every other change to that language of the document (editing, approving, applying TM, machine translation, TM unlock, tag repair, paragraph and image edits, key values) is refused with 409 awaiting_review on the web, the API, the CLI and MCP.
  • TM match (tm_match) - pre-fills and locks TM hits before any engine runs, so qualifying segments are settled without an LLM call. Tunable per step in the builder’s TM match policy panel: a fill threshold (fill matches at or above this score; 100 = exact only), a fuzzy lock mode for below-100 fills (none = a suggestion with no lock, soft = enters LQA, policy = the same lock the 100 band gives), lock in-context matches / send 100% matches to LQA / context floor overrides, and a TM pool selection (which readable project memories this step reads; blank = all readable). Each override left at inherit follows the matching global setting, and a new step is seeded with a snapshot of the current globals. A fuzzy fill only lands when the segment and the memory carry identical numbers, URLs, and variables. If a memory entry is edited after it filled a segment, the editor marks that segment TM changed since fill; running the step again re-fills unreviewed (machine) segments from the edited entry, while approved or edited segments keep their text. On a full-text document (one whole-body segment) the step cannot fill or lock anything, so it does something else instead: it reads the body, looks up each sentence, and offers the 100% matches to every later llm_agent step as approved wording to reproduce. The step honors tm_pool_selection within the readable pools; an empty selection offers nothing. It is an offer, not a guarantee, and nothing yet checks whether the engine honoured it. If a string must be exact, use a segmented document. Offers are withheld from each step that redacts PII, because an offer reproduces the document’s own sentence verbatim; the run says so rather than reporting a silent zero.
  • External (external) - dispatches the run to a linked vendor and parks it until the translated work returns.

Each step has its own engine, model, prompt and failover model. Output flows step → step; oversized documents auto-chunk and reassemble. Prompt placeholders:

{text}   the content to process (source on step 1, prior output afterwards)
{prior}  alias of {text}
{source} the original source     {source_locale} / {target_locale}
{glossary} the applicable glossary constraints
{tm_offers} full-text only: the 100% TM matches offered as approved wording

The segment text ({text} and {prior}) is automatically wrapped in <content> markers unless the template already wraps the placeholder itself (for example <text>{text}</text> or a code fence), which is how an author opts out.

Each llm_agent step carries an optional concept-glossary renderer toggle (off by default). Turned on, the {glossary} block renders the run's matched glossary concepts - audience-gated (a human-only term never reaches the model), ordered (do-not-translate and forbidden terms first) and capped by a per-step concept cap (default 10) and token cap (default inherits the install glossary_prompt_token_cap) - instead of the plain term list, and the enforced glossary set becomes exactly the set the model was shown (so a downstream step never flags a term the translator was never given). Off, the block and the enforced set are byte-identical to before. A step with it on shows a “concept glossary” badge in the workflow builder.

Important: a custom LLM-agent step prompt must contain {text} or {prior}. Without it the model receives no source, its output reads as a refusal and is withheld, and the run trace flags the missing-source footgun. The prompt-authoring assistant drafts a step prompt from a plain-language description (and keeps every placeholder verbatim).

Automatic review holds

Besides the tag, placeholder and number checks, three checks send a machine translation to needs review with a check badge. They only run on output from a real engine, keep the text out of translation memory until a person saves or approves it (which clears the badge), and never change the file: the export still writes the translation.

  • Ambiguous date: a date written in numbers whose day and month could be swapped (10/11/2026) and that a reader of the target language would read differently from what the source means, for example US 10/11/2026 (11 October) written as German 10.11.2026 or kept as 10/11/2026 in Hebrew or Thai (both read as 10 November). A correct conversion (11.10.2026), a date with the day above 12 (25/12/2026) and the same day-first convention on both sides pass.
  • Line breaks differ: the translation has more or fewer line breaks than the source, for example a one-line table cell that came back on two lines. Web pages, XML and Markdown are not checked (a line break there is just a space), and a subtitle cue joined into one line passes.
  • Words joined at a formatting change: in German, Dutch, Finnish, Korean, Turkish, Arabic and Hebrew, two words that the source separates with a space next to a change of formatting (a bold word, for example) came back written together and do not form a real compound (“bevor Siedas Fenster”). Real compounds such as “Benutzername” and attached particles pass.

QE routing gate and quality judges

A Translate (llm_agent) step can score every segment it produces: tick QE routing gate in the builder and set its QE threshold (whole numbers 0 to 100 only; invalid values and decimals such as 70.0 are refused, default 70). A segment at or above the threshold carries on; one below it lands in needs review, and the document still ships (the gate routes segments, it does not hold delivery). The QE judge engine picker chooses who scores:

  • (reuse step provider) or any LLM: an LLM judge scores against an MQM-aligned prompt.
  • A quality judge: a Jev (TypeSafe, hosted) engine or a Jev-compatible local server (SemIf, Kev) engine, added on Setup AI. Jev answers five fixed questions with a probability for every answer, and the app turns them into the score. A judge engine only ever appears in this picker.
  • The older value qe_provider="jev" (the TYPESAFE_API_KEY environment setup) keeps working; without that key, scoring skips.

What a Jev judge's verdict means: pass (at or above the threshold with every dimension sure), fail (below the threshold, even with an unsure dimension: it goes to review), undecided (at or above the threshold but a dimension was unsure: never a pass, but the segment carries on unchanged, is not sent to review, shows a qe badge reading QE undecided on hover, and counts as QE skipped) or not scored (the judge was unavailable, the spend cap was reached, or the answer was unreadable or too unsure to score: the segment carries on without a score and counts as QE skipped). The exact rule, rendered from the code's own numbers, is on each judge's Inspect page, where Try it scores one segment the same way. Cost: an LLM judge makes one call per segment; hosted Jev is priced and counts against the spend cap; a local LLM or a local Jev-compatible server is free and never capped. To run your own judge (SemIf on a GPU box, on the same PC or over Tailscale), see Run your own Jev-compatible server.

The QE gate (both backends) runs only in the SEGMENTED workflow path; a full-text step with qe_gate on makes no judge call.

Jev is text-only and English-primary, with no error spans or prose findings. The qe_jev_enabled=0 setting disables calls for the qe_provider="jev" environment setup only (its qe_jev_confidence_floor defaults to 0.6); a Jev engine is switched by its own Enabled box and can carry its own floors. MQM LQA (Check steps) and its correction loop remain separate.

Jev checks untranslated text, tags, placeholders and number/time parity before the judge. Identical single tokens, acronyms and brands are advisory, with or without a glossary. Identical multi-word text (normalized whitespace/case) blocks across different base languages. Other structural failures are MAJOR and block a pass at any score; the judge still runs. Disabling the judge does not disable structural checks: an unscored block says judge did not score. Number and time parity keeps the number checker's own grade: a changed value (5 to 50), a changed time (6:45 to 7:45) or an AM/PM swap is MAJOR and blocks, while two forms are advisory and only flagged for review: a dot-format time that equals the source time (klo 18.45, 18.45 Uhr) and a number from 0 to 10 written as a word (2 to deux) in a supported language. Every other number finding blocks as MAJOR, including a dropped or added number, a wrong dot time, regrouped digits (1-10 to 110) and an ambiguous rendering. Jev also reads what a number means, and each of these is MAJOR: a clock time dropped from the target (hour words, an hour-only form such as 20 heures and Chinese or Japanese clock times are read as the time), a date whose day, month or year changed (the order is judged for the target locale, so 3/14/2026 to 14.03.2026 is correct and 3/14/2026 to 15.03.2026 blocks; a dot date is day first, ISO and Chinese, Japanese and Korean written dates are read the same way, a date written out in words passes when its day and year match, and a bare en source locale with both numbers 12 or below leaves both orders open), a lost minus sign (a hyphen-minus, U+2212, an en dash or a parenthesised currency amount is negative, and a word such as minus or moins stands in for the sign), and a swapped or dropped currency ($, USD, US$ and dollars are one currency, $ to EUR is not; placement and spacing per locale do not matter). A minus the target adds is not judged. AM/PM counts only on hours 1 to 12, and a bare am after a German or Dutch time is not a meridiem. In scripts written without word spaces, a run of at most 8 characters (ignoring trailing punctuation, ASCII or full-width) is one token, so an identical copy is advisory; longer or internally punctuated text is multi-word and blocks. HTML void elements such as br are one tag kind however written. Numbers-only text, URLs, codes and applicable glossary DNT terms are exempt from the untranslated check. Meaning promotion lifts accuracy none, minor or unsure to major before the low-confidence skip.

Auto-fix failures

Read QE cards and auto-fix history headlessly with doc show ID --detail (also --json), /api/documents/{id}/segments?detail=segments, or MCP work_status(document_id=ID, detail=true). To see what each step of a run actually changed, open the run page and click Highlight differences: it compares two steps segment by segment, word by word (inserted text is underlined, removed text is struck through), by default the newest translating output against the previous one, and a picker chooses any two steps. Headless: workflow step-diff ID (add --from / --to step run ids), /api/runs/{id}/step-diff, or MCP work_status(run_id=ID, step_diff=true). It only reads text the run already recorded; nothing is re-run and nothing is spent.

A Translate step whose QE judge is a Jev judge can repair its own failures. In the builder, under the QE judge engine, tick Auto-fix failures (the block appears only for a Jev judge). A segment that fails the gate is handed to a post-editor LLM, which sees the source, every version so far and each Jev score, and writes a new version; the same judge re-scores it, for up to max rounds (1-5, other values are refused; default 3). Invalid rounds are refused, not clamped; blank uses 3. The post-editor must name an existing LLM engine. The post-editor defaults to the step's own engine; pick any LLM instead. It must be an LLM: a machine-translation or judge engine is refused, and a step whose own engine is machine translation must name an LLM post-editor (saving refuses otherwise; auto-fix never switches to another engine on its own). Cross-check also asks the post-editor LLM for its own score of each accepted rewrite, shown to it as a second opinion. No cross-check runs before a rewrite exists or after the post-editor fails.

Unknown QE judge names and missing engine refs are refused at save. A disabled judge saves with a warning. Auto-fix saved without a QE gate or with a non-Jev judge is accepted by the API, CLI and MCP (only the web builder hides the option) but warns that it cannot run. If a gate scores no segments, the run warns and QE flags name the skip reason.

A version that passes the gate replaces the segment's text and the segment passes. Anything still failing goes to review as before: the reviewer gets the best attempt only when the judge was sure of it and its score is strictly higher than the original's (a reply identical to the previous version ends the loop without another judge call), and every round's score and text either way, on the editor's auto-fix tried N rounds badge (a fixed one reads auto-fixed in N rounds). A fix must pass the same checks as normal output (refusals, inline tags, page dumps, glossary and do-not-translate terms), or it is rejected. Confident major dimensions are fixed even alongside unsure dimensions, which are left unchanged and flagged for review. An improved rewrite may be kept with those baseline unsure dimensions still flagged; it cannot pass. Without a confident major, an unsure verdict skips auto-fix. An undecided segment never enters the loop. Also skipped: a step that redacts PII, and output already withheld as a refusal. When the loop does not start, the editor shows auto-fix skipped with the reason (for example, the judge was unsure, or the step's QE judge is no longer a Jev judge). The spend cap: a loop that can cost money (hosted Jev, or a paid post-editor) does not start, and stops between rounds, once the monthly cap is reached; a fully local loop (a local Jev-compatible judge plus a local post-editor) costs nothing and keeps running, like every other free call. Every post-editor and judge call lands in the {{ names.ledger }} with its round number, and the cost counts toward the step. CLI: --qe-autofix, --qe-autofix-provider, --qe-autofix-max-rounds, --qe-autofix-cross-check on workflow add-step / edit-step; API and MCP: the qe_autofix, qe_autofix_provider, qe_autofix_max_rounds and qe_autofix_cross_check step fields.

Parallel routing & the workflow canvas

The builder page draws the workflow as a canvas, not just a list. Steps carry a grip handle: drag one to reorder it, or drop it onto another step's lane to make the two run together. Every drop saves immediately and re-validates the whole graph, so an illegal move bounces back with the exact reason rather than leaving a workflow that only fails at run time. The move-up / move-down buttons on each step row do the same thing without a mouse.

Parallel groups

Two adjacent Check steps that share one parallel-group slug run at the same time against the same translation; the run continues when both have finished. Use it to score one output on two rubrics at once - a general LQA lane and a terminology lane, say - without paying for two sequential passes.

  • Exactly one member may carry the branch. The other lane's score is still recorded and still usable in a condition - it just does not decide where the run goes, because two lanes both routing the run is not a graph.
  • A member with nobody adjacent sharing its slug shows its chip greyed as not active and simply runs in order. It is a warning, not a failure.
  • Conditions name a lane explicitly with step:<key>:failed when prev_lqa / prev_qe would be ambiguous about which check they mean - which is exactly what happens once two checks ran at once.

Branches may only target a step that appears earlier in the list - there are no forward jumps. To loop, put the check after the step you want to re-run and point its on-fail back at it; loops are capped by a per-step max-visits ceiling and an absolute total-step cap per run, and hitting either ends the loop gracefully rather than spinning. Max visits bounds a step's own executions in every role it plays - as the target a loop-back jumps into, and as the check that owns the branch. A check that has already run its ceiling is not run again and the run ends there; a translate or fix step at its ceiling is simply skipped and the run carries on, so the check still judges the last text that was produced.

A repair that changes nothing does not get a second roll of the judge. When a loop-back brings a check back to text that is byte-for-byte text that same check has already judged in this run, the fix step did nothing - so the verdict those exact words already got is carried forward with the reason stated on the step, and the loop ends. That matters because an LLM judge is not deterministic: re-asking it about identical text until it happens to pass is a lottery, not a quality gate. A repair that genuinely changed the text is still re-judged normally, and a carried pass simply ends the loop and moves on.

When a run ends with an LQA check still failing, the run is held - and held means the translation does not ship. It is the check’s last VERDICT that decides this, not the shape of the workflow, so it covers every ending: the repair that changed nothing, a loop that ran out of visits, a check that hit its own ceiling, and a check that simply fails and stops or carries on. A check that could not be run at all - the judge was configured but never answered - is held the same way, and says so: the translation was never judged, which is no safer than one a check judged and rejected. A check your own run-condition skipped is not held: you asked for it to be skipped. The QE gate on a translate step is a different thing and is not a hold - it scores each segment and sends the weak ones to review while the document still ships, which is what it is for. The workflow itself still goes where you told it to go; what is withheld is the delivery. The run says why on the run page; every segment it produced is marked needs review with a badge naming the check; and downloading the translated file is refused, in words that name the ending it is refusing - including with “export anyway”, which exists for a missing translation, not for one a check failed.

Two things lift a hold, and only two. Approve or edit every held segment in the editor, or run a workflow whose own check passes over the new text - the check has to have judged the text that run actually saves, so a polish or fix step that rewrites a segment after the check leaves that segment held. A step that runs after the check and rewrites nothing withholds nothing, so where such a step sits in the workflow never changes the answer. Re-running a workflow that has no check, or whose check fails again, does not lift it - otherwise “run it again” would be a one-click way around the quality gate. It cannot work the other way either: a segment you approved or edited is never sent back to needs review by a later run - including a segment you edited during a pause in the very run whose check then failed, which keeps your text and your protection and simply carries the badge - so re-running a workflow can neither lift a hold nor re-impose one you have already cleared. Approving a segment also clears the badge that hold left on it. One case widens the release rather than narrowing it: when the run was held because a translate step’s own QE correction loop ran out (that is a loop ending, not the per-segment routing above), a later run of that same workflow whose QE gate passes over the new text lifts it too - the workflow that created the hold can clear it.

Vendors & external steps

Some content should not be machine-translated and shipped - it should go to a human translation or review vendor first. Vendors make that a first-class part of a workflow: a run can dispatch its packaged text to a linked vendor, wait for a signed return, and resume - with the price, the spend approval and any rework handled inside the run rather than over email.

  • A vendor is a first-class record (Vendors) - a name, a connection (endpoint URL + a Fernet-encrypted signing secret), a transport protocol (native automated wire, or manual carry-out/carry-in), an MSA rate card, and the customers it may serve. An external step can only pick a vendor linked to that document's customer.
  • Dispatch is a workflow step - a step of type external packages the segments, sends them, and pauses the run until the return arrives. Vendors are a workflow capability, not a side channel.
  • Lifecycle: dispatch → (optional) quote & approve → return → (optional) reject & rework. A quote-gated vendor parks the leg as QUOTED until an operator records the quote and approves the spend - the deliberate money decision, separate from dispatching. Rework rounds are capped (default 1), then the run escalates to a human review pause.
  • The return is guarded. Translated segments come back by signed webhook callback, by vendor poll, or by manual re-upload - all through one write seam that honours the same protection law a normal translation does. Inbound XLIFF 1.2 is accepted anywhere JSON is, and outbound legs can ship an XLIFF package.
  • Money is two lines - model (AI) spend and vendor post-edit (Human) spend are tracked separately (AI + Human = total). The Human figure is an estimate, derived from the leg's TM-leverage band breakdown priced through the rate card, until the vendor reconciles an actual on its return.
  • Off means removed, not corrupted. With the vendors switch off, every vendor surface (the pages, /api/vendors, the inbound webhooks, the CLI) 404s/refuses and no new outward vendor traffic is sent - a run reaching an external step fails with a readable reason rather than dispatching. Existing vendors and their data are preserved, but the DB-only lifecycle sweep keeps running even while off: an already-dispatched leg that reaches its expiry is escalated to a human-review pause rather than left hanging. Turn the switch back on and dispatching resumes.

Segmentation (SRX)

In segmented mode each paragraph is split into sentence-level segments. By default a built-in regex splitter is used (terminators . ! ? plus CJK 。！？). It does not break after common abbreviations: e.g., i.e., incl., ext., approx., vs., titles such as Mr. and Dr., single-letter initials, and Max., Min., No. or p. before a number, plus source-language ones such as German z. B. and bzw., French p. ex., Spanish Sra., Italian Sig. and Dutch bijv.. A sentence that really ends with etc. still splits. Files imported before these rules (October 2026) keep their original split, so their exports do not change; re-uploading a file splits it with the new rules. Admins can switch to standards-based SRX 2.0 under Settings → Segmentation:

  • The shipped default ruleset reproduces the built-in splitter, abbreviation rules included, so turning SRX on does not change existing segmentation. A custom .srx replaces these rules entirely.
  • Upload a custom .srx (max 1 MB) for language-specific rules; it is parse-validated before it is accepted.
  • Rules select per source locale via SRX maprules with cascade. ICU-flavored regexes translate the common unicode property classes (\p{L} \p{Lu} \p{Ll} \p{N}) to Python regex.

Segmentation profiles package a rule configuration and can be selected per project.

Inspecting a quality judge

Every judge card on Setup AI has an Inspect button (admins only). The page has four parts:

  1. What Jev is asked: the five questions (accuracy, fluency, terminology, style and the yes-or-no meaning check), what every level means, and the exact request body. The API key only ever rides in an Authorization header and is never shown.
  2. How it decides: the confidence floor, the meaning-check promotion, how an unsure answer is handled (it never passes; an undecided segment carries on unchanged, its QE flag reading QE undecided, and counts as QE skipped; a failing one goes to review and never enters auto-fix), the score formula with each category's penalty, and the step's pass threshold. It is rendered from the code's own numbers and this engine's settings, so it always matches what the QE gate does.
  3. Try it: enter a source, a translation, both locales and a threshold (default 70). Source and target must be text; locale codes must be in the language catalog (for example en, zh-Hans or pt-BR), not language names such as english. One segment is scored exactly as a QE-gated step would score it, and you see the request sent, the raw answer, each dimension's level, the verdict (pass, fail, undecided or not scored), the cost and latency, and the exact prompt the auto-fix post-editor would get for round 1. Hosted Jev bills a fraction of a cent per try and stops with a clear message once the spend cap is reached; a local server is free. Tries are limited to 20 a minute per person, one at a time per engine (one hosted try at a time), and stop after the engine's timeout plus 2 seconds. The limits live in the running server (a single-process install); across processes or machines the spend cap remains the money backstop for hosted Jev.
  4. Ledger: a link to the {{ names.ledger }} filtered to this engine. Tries are recorded (while the Ledger is on) as action jev-try.

The same inspection is available as engine inspect and engine jev-try on the CLI, GET /api/admin/engines/{eid}/inspect and POST /api/admin/engines/{eid}/jev-try, and the MCP manage_install actions inspect_engine and jev_try (a try bills, so over MCP it first returns a plan; pass confirm: ["jev_try"] once the user agrees).

Source-context harvest - the differentiator

When a connector ingests content, it harvests the source system's own metadata - the article/page title, a section (e.g. the Airtable table), and labels - straight into the document's translation context package. That context is then layered into every segment's prompt, so the model translates the Zendesk article “How do I reset my password?” knowing it is a support FAQ titled exactly that, with its faq, accounts labels in view. No other TMS documents an external system's metadata automatically enriching the translation as a general, per-connector mechanism - here it is one.

  • Allowlisted & sanitized. Only a small, named set of fields per connector is captured (never the raw record); every value is validated, length-capped, and neutralized against prompt break-out before it is stored. Harvested metadata is data about the content, never instructions (it renders under a fixed <translation_context source="…"> header the model is told is reference-only), and the record URL is stored for humans but never sent to the model.
  • Layered, not overriding. Harvested context sits at the document layer - an explicit translation request or a customer/content-type context card always outranks it, so operator intent wins while the harvest fills the gaps.
  • Per-connection toggle. Each connector exposes a harvest_context setting (on by default; set 0 to disable). With harvest off - or when a record carries nothing harvestable - the prompt is byte-identical to a run without it.

Applies to every connector kind through the same shared mechanism - Confluence included: its space name, parent-page path and labels now flow through the shared harvest seam, not a bespoke one.

Project automation - a project's content source and schedule

Open a project and choose Automation. Pick the connection the project pulls its content from and writes translations back to, then choose when it runs: times of day on chosen days of the week, or every N minutes. Times are UTC, and your own local time is shown beside each one. A run translates only what is new or changed (delta), or everything again (full; matches already in the translation memory cost nothing). Run now, pause and resume are on the same page, and the run history below lists when each run happened, why, and what it wrote, held for review or failed.

  • One connection, many projects. When a connection already feeds another project, the next project gets its own private copy of it (same credential, its own tracking). The first project to reach an item owns it: a later project skips that item and the run says so, so two projects never overwrite each other. When a run is blocked this way, both projects are notified once (automation.blocked), and a manager of the owning project (or an admin) can hand the items over with one click on either project's Automation page; the receiving project then owns them. A manager can bind an organization-wide connection to a customer's project; it always runs on the project's own copy.

  • Nothing spends by surprise. A schedule is off until you turn it on, and turning it on never starts a run at once. The project's monthly budget is checked before every run, and you can set a per-run spend cap (there is no default cap). Session limits and the sign-out warning

Every authenticated API request counts once toward a per-identity rate limit. api_rate_limit_per_minute (default 120) covers uploads and engine work; api_read_rate_limit_per_minute (default 600) covers reads and cheap writes. Set either to 0 to disable it, on Security, API admin config, or CLI config. Both accept at most 100000 per minute. Invalid stored values use the default. Counters live in process memory, reset on restart, and are separate per worker. Excess requests return 429 with Retry-After. Session-only web requests and health/readiness/metadata endpoints outside /api are not limited.

With login required, two limits end a session. session_idle_minutes (default 240, 0 = off) signs a person out after that long without activity; typing on a page counts as activity. session_max_hours (default 24, which is also the most allowed, 0 = no separate maximum) is the maximum session length, counted from sign-in; activity never extends it. The inactivity limit is at most 1440 minutes (24 hours). Independently of both, the session cookie is valid for at most 24 hours after the last page load, so with session_max_hours at 0 an unused session still ends after 24 hours. Both are on the Security page's Sessions card, in config set, and in the /api config surface. Two minutes before either limit ends, the page shows a warning with a countdown; for the inactivity limit “Stay signed in” extends the session. When a session ends, the page behind the “You have been signed out” message is hidden and the message cannot be dismissed, so nothing stays readable on an unattended screen; signed-in pages are also sent with Cache-Control: no-store, so the browser's Back button does not bring them back. After a sign-out, text you had not saved on the page is kept for that browser tab and offered back (Restore or Discard) after you sign in again. The page reads GET /auth/session (read-only; asking never extends a session) and extends with POST /auth/keepalive (CSRF-protected). Sign out (the profile menu) is a CSRF-protected form and ends the account's sessions on every device; opening /auth/logout directly only shows a confirmation page.

Password rules

Accounts that sign in with a password here follow the install's password policy. Accounts that sign in through OIDC, SAML or LDAP have no password here and are not affected. An admin sets the rules on the Security page's Passwords card, with config set, the /api config surface or MCP manage_install: password_min_length (default 12, 8 to 128), password_require_classes (how many of lowercase, uppercase, digit and symbol, default 0), password_block_common (default on: refuses a password that is commonly used, including common words with digits or symbols added, repeated or keyboard sequences, one that contains your email, or is your user name with digits or symbols added, and one containing the full product or company name), password_history (your last N passwords cannot be reused, default 5, at most 24; only one-way hashes are kept; a new password must always differ from the current one) and password_max_age_days (default 0 = never expires, as NIST recommends). Spaces and letters from any language are allowed, up to 1024 characters. When a password is refused, the message says exactly which rule it broke. After an admin resets your password, or when it is older than the maximum age, you choose a new one at your next sign-in before anything else.

Who can change a password here: only people whose account signs in with a password stored on this site. They change it on the Account page and must type the current one. People who sign in through single sign-on (OIDC or SAML, including accounts your identity provider manages with SCIM) change their password with their organization's sign-in provider, and LDAP accounts change their directory password in the directory; the Account page says so instead of showing a password form, and a local password never signs those accounts in. Only an administrator can move such a person to a password on this site, by resetting their password (user reset-password, or POST /api/users/{uid}/reset-password): that turns the account into a local-password account, is recorded in the audit log as user.auth_source_changed, and from then on the person signs in with that password instead of single sign-on. An email invitation never does this: an invitation for an address that already signs in through single sign-on or LDAP, or for an account that has been deactivated, is refused and the link stops working. The host application's service identity (trust sign-in) has no password and cannot be reset or invited.

Two-step sign-in (TOTP)

Password sign-in has two limits: five failures for a typed name from one address in 15 minutes block that pair for 15 minutes; 20 failures across addresses in a rolling 60 minutes lock unknown devices for 15 minutes. Consecutive account locks double to 30 then 60 minutes, capped at 60. The account limit persists across restarts and resets after successful sign-in. A signed known-device cookie lasts 30 days and bypasses the account limit while still facing the address limit. Administrators can use Users > Unlock sign-in; a host operator can use user unlock <email> even when locked out. Admin password resets also clear account locks. Lock/unlock is audited; lock notifications email the owner when mail is configured.

Two-step sign-in adds a 6-digit code from an authenticator app (Microsoft Authenticator, Google Authenticator, 1Password, Bitwarden, Aegis and other standard TOTP apps) after the password, so a stolen password alone is not enough. It is for accounts that sign in with a password here: local accounts and LDAP accounts. People who sign in through single sign-on (OIDC or SAML) are not asked for a code here: their identity provider's own multi-factor sign-in applies, so set MFA up in your identity provider. API keys are not affected: a key is a separate credential for scripts and integrations, not a sign-in; revoke a key on the Account page or with apikey revoke if it may have been exposed. There is no "remember this device": every sign-in asks for a code.

  • Turn it on for yourself on the Account page: choose Set up two-step sign-in, re-enter your current local or LDAP password, then scan the QR code with your app or type the setup key shown under it, then type the app's current code. The setup key belongs to that one set-up: reloading the page keeps it, but starting set-up again (a new sign-in, a new password check, another browser) shows a new key and the old one stops working, so scan the key you were shown last. You then see ten recovery codes, once: save them somewhere safe. Each recovery code signs you in once if you lose your phone. From the same card you can make a new set of recovery codes, or turn two-step sign-in off; both need a current code. Turning it off also needs your current password. Turning it on or off ends your other sessions. Changes and replacement recovery codes are emailed to you when SMTP is configured. LDAP accounts prove their password through a directory bind. Pure SSO, SAML and OIDC accounts use their provider's MFA; they cannot enroll or turn off a factor here. The same goes for an account your identity provider manages through SCIM that has no password on this site, and mfa_required never signs such an account out. An account with no password here cannot set up two-step sign-in at all: ask an administrator for an invitation or a password reset first.
  • Current-password checks share a five-attempt budget across forms and client addresses. After too many failures, sessions end and further attempts are refused for 15 minutes, including correct passwords. Each refusal is audited.
  • Invitations cannot replace an active account's password. Administrators should use Reset password instead, on the Users page, API, or CLI.
  • Signing in: after your password, enter the code your app shows (or a recovery code). You are not signed in until the code is accepted. Finish this step within 5 minutes; if the time runs out you are sent back to the sign-in page and simply sign in again. Each code works once. Wrong codes count toward the same lockout as wrong passwords (5 attempts, then 15 minutes), and each account also has its own limit: 10 wrong codes within 15 minutes, from any address, lock code entry for that account for 15 minutes, and the account owner is emailed (when email is set up). A recovery code still signs you in while code entry is locked.
  • Requiring it: an admin sets mfa_required on the Security page's Two-step sign-in card, with config set mfa_required admins, or through the /api config surface: off (the default; anyone may still turn it on for themselves), admins (every administrator must use it) or all (everyone who signs in with a password). A person who must use it and has not set it up is asked to set it up right after their password, before they can reach anything else (each sign-in gets its own setup key, so a set-up someone abandoned is never shown to the next person), and cannot turn it off while the requirement applies. The requirement also applies to people already signed in: when it is raised, or someone is made an administrator under admins, a session that did not use a code is signed out and they sign in again. An account with two-step sign-in on here cannot be taken over by an OIDC or SAML sign-in; it keeps signing in with its password and code. Set it up for your own account before you require it for administrators.
  • Lost phone: sign in with a recovery code, or ask an administrator to reset your two-step sign-in (Users page, Reset in the Two-step sign-in column; DELETE /api/users/{uid}/mfa; or user mfa-reset). A reset deletes the authenticator setup and recovery codes and signs the person out everywhere. If someone else may know the password (an unexpected lock, or a lost phone together with a leaked password), an administrator resets the person's password first and only then their two-step sign-in: otherwise whoever signs in next with the old password could set up their own authenticator. If single sign-on is refused because two-step sign-in is on (for example after moving from LDAP to SAML), an administrator resets the person's two-step sign-in and single sign-on then works. A sole administrator locked out of every factor is recovered on the server itself with the command line: python -m app.cli user mfa-reset <email> --yes.

The shared secret is stored encrypted with the install's encryption key; recovery codes are stored only as one-way hashes. The audit log records mfa.enroll, mfa.success, mfa.failed, mfa.recovery_used, mfa.recovery_codes, mfa.disable, mfa.reset, mfa.locked, mfa.session_ended, login.sso_refused and mfa.challenge (the password was right and a code was asked for), plus the setting change; it never records a code or the secret.

OIDC single sign-on

Authorization-code + PKCE against any standard IdP (Okta, Entra ID, Auth0, Keycloak, Google…). Enter the issuer URL - discovery is read from <issuer>/.well-known/openid-configuration - and the client ID from your IdP app registration, then register the callback {{ external_base_url }}/auth/oidc/callback with the provider. A client secret is optional (PKCE is always used). First-time SSO users get the default role from Settings; a local admin account always keeps password login, and SSO never takes it over.

From the command line, every admin ldap config, admin oidc config and admin retention config write changes a security-sensitive setting, so it is validated and then confirmed like config set; a script with no terminal must add --yes or nothing is written. For scripted account creation, user create --password-stdin reads the initial password from standard input so it never appears on the command line; with no password at all the account has no local login (single sign-on or SCIM only) and a warning says so.

Each OIDC account is linked to the provider's subject id (sub) the first time it signs in, and later sign-ins are matched by that id, not by email. That first link (a new account, or an existing account with the same email) needs the provider to mark the email as verified (email_verified); preferred_username is never used. An account already linked to a different subject, and any LDAP or SAML account, is refused and the refusal is audited (login.sso_refused); a new link is audited as login.sso_linked. If your provider assigns every address itself and never sends email_verified, an admin can turn on Trust this provider's email addresses on Security (or admin oidc config --trust-unverified-email on --yes); use it only for a single-tenant provider, because while it is on anyone who can set their own email at the provider can claim an account with that email that is not linked yet. Accounts that existed before this change link on their next verified sign-in; with a provider that never sends email_verified (Entra ID by default) they are refused until the switch is on. Password accounts, including the built-in admin, are not affected, so an admin can always sign in to turn it on.

Set app_base_url on Security to the external URL of this install. It is the authority for invitations, SAML/SCIM discovery, UTCP tool URLs and OAuth callbacks; the request Host is the fallback when blank. Explicit SAML EntityID/ACS settings still win. An HTTPS base also makes SAML Destination validation work behind a TLS-terminating proxy.

Ingress trust is configured only on the host: security_allowed_hosts pins valid public hostnames and trusted_proxy_ips lists trusted proxy IPs/CIDRs. Use local config set with confirmation or the corresponding LOC_TMS_SECURITY_ALLOWED_HOSTS / LOC_TMS_TRUSTED_PROXY_IPS environment overrides. Local proxy trust changes apply live to identity and scheme; environment changes require a restart. API and MCP writes are refused even with confirmation. There is no loopback exemption from the Host pin. The exact /health and /ready probes may use any syntactically valid Host; they bypass only the Host allowlist. Malformed Host syntax still fails. Recover with a corrected or empty host override / a local config apply file, then restart. Invalid ingress overrides log ERROR and resolve to empty without stored fallback; /admin/health detail reports ingress_config: invalid <key>. With app_base_url configured and the effective pin empty, detail includes "host_pin":"unset" and boot logs one WARNING; otherwise that key is absent. Local loopback installs always accept localhost, 127.0.0.1 and [::1], plus the configured base URL and allowed hosts. Other hosts receive 400, including probes. Add your Tailscale name or address with the host CLI or environment override before accessing through that alias. Server installs keep the explicit pin behavior above. Fresh local accounts require a password change at first sign-in; existing accounts retain their credentials and password-change flags after upgrade. A data-directory override alone does not disable login. Test mode requires the explicit LOC_TMS_TEST_MODE flag and a loopback bind. Remote binds always enforce authentication. See docs/LOCAL-INSTALL-SECURITY.md for the secure Compose proxy command and private storage permissions. Non-empty Host list writes must include the configured app_base_url host (case-insensitive, port-independent): add that host, or clear/repoint app_base_url. Empty remains settable. Recover from the host shell with config set security_allowed_hosts "", which runs outside the ASGI boundary; clear any environment override too. For supported profiles B/C, set app_base_url and security_allowed_hosts, including every intended access alias. Non-empty all-separator Host lists are invalid. Every uvicorn launch uses --no-proxy-headers; the application boundary alone handles forwarding with trusted_proxy_ips as its only proxy setting.

login_trusted_networks (IPs/CIDRs, IPv4 /8 or narrower, IPv6 /32 or narrower) exempts a shared NAT such as a campus egress from the 200-failure per-source sign-in budget only; per-name and per-account lockouts still apply. Set it on the Security page (Access control) or with config set (confirm to set).

LDAP / Active Directory

When enabled, the login form tries the directory first for each sign-in (search-then-bind): bind as the service account, search the base DN with the user filter, then re-bind as the matched entry with the typed password. On success it provisions/updates a local account with the default role and signs the user in. Any LDAP failure falls back to local password login, so the built-in admin always works and an outage never locks you out. A local admin password account is never taken over by an LDAP identity with the same email. Use ldaps:// (or StartTLS) in production; plain ldap:// is allowed for dev. LDAP also needs an optional library: on a container install, build the image with --build-arg WITH_LDAP=1, or the Security page refuses to turn LDAP on.

SAML 2.0 single sign-on

{{ brand }} also acts as a SAML 2.0 service provider for identity providers that speak SAML rather than OIDC (Okta, Entra ID, ADFS, and similar). You enable it and enter the IdP's metadata on the Enterprise panel, then register {{ brand }}'s assertion consumer service (ACS) URL with the IdP. On a valid assertion it provisions or updates a local account with the default role and signs the user in. SCIM 2.0 provisioning

SCIM 2.0 lets your identity provider create, update and deactivate {{ brand }} users and groups automatically, so joiners and leavers are managed from the IdP instead of by hand. It is turned on from the Enterprise panel (which takes the operator-key step-up and is OFF until you enable it). The panel does not issue a token: your IdP authenticates to the /scim/v2 endpoints with a Bearer token that is a scim-scoped API key you mint on the host with loc-tms apikey issue --user <admin-email> --scopes scim, owned by an active admin.

Full-install recovery (local CLI)

Air-gapped deployment

For confidential environments set the local engine as the default provider. Then translation, OCR, glossary sense-selection and LQA all run on your own hardware - no request ever leaves the network. The app itself has no external runtime dependencies, so it can run on a network-isolated machine.

Part 2 · HTTP API reference

Every screen is backed by HTTP endpoints. The /api surface below is what the remote CLI (loc-tms --remote URL --token lsu_...) and companion apps call; the in-process CLI calls the same service functions locally, so a command behaves identically over either transport. The remote CLI takes its key from --token, --token-file PATH (the file's first line), or the LOC_TMS_TOKEN env var, in that order; --token is visible in process listings and shell history, so the CLI warns when it is used. Plain http:// is allowed only for loopback and tailnet hosts (*.ts.net); for any other host use https:// or pass --insecure, and the client never follows redirects, so the key cannot move to a different scheme or host. Responses are JSON with an ok flag; errors return {"ok": false, "error": "…"} with an appropriate status code. Some refusals additionally carry a stable, machine-readable code field beside error (today the keys-export image-cap refusal returns "code": "key_image_export_max"); where present it also rides on the remote CLI's --json error object, so a script can branch on the stable code rather than the human message.

API keys, the remote CLI and MCP have the same project visibility as your account. With project scoping enabled (the default), translators, reviewers and viewers see projects they created or joined. Customer-bound accounts see their customer's projects. Missing and inaccessible project resources return 404; lists omit them. Ask a project owner or manager to add you under Members if a project you need is missing.

Authentication & scopes

Authenticate with a token in the X-Loc-Token HTTP header (never a query string - those leak into logs). Two credential kinds:

  • Per-user key (lsu_…) - resolves to a user for attribution and RBAC. This is what the remote CLI and the document/MCP front door use.
  • Legacy shared connector token (lsk_…): retired for connector operations, connection lists, job results and translation. Companion apps must use a per-user key from Account, subject to its role and org/customer access.

Scopes. A per-user key carries a space/comma list of grants. There are four:

  • api - always implied, the base inbound grant. It reaches the connector endpoints, POST /api/translate/text, GET /api/jobs/{jid} (job status, identity-only) and GET /api/capabilities/{slug} (a deliberate carve-out - an agent reads the driver's manual before it holds the scopes to act); it is 403 everywhere else.
  • docs - the document endpoints (POST /api/documents, …/translate, …/download, /api/languages, /api/formats, the image endpoints) and the entire remote-CLI surface - which is most of the table below.
  • keys - the key-based-project group and the Delta API: /api/projects/{pid}/keys…, /api/keys/… and GET /api/projects/{pid}/changes. A separate grant on purpose, not a corner of docs: a CI sync consumer holding a key-scoped token has no business uploading and downloading documents, and a document integration has no business reading the whole string catalogue. Neither api nor docs implies it.
  • admin - the top grant, gating the sharpest identity/admin verbs (GDPR export/erase, retention purge-now, apikey revoke-all, the account-security changes (user create, role change, password reset, MFA reset, invite and re-enabling a disabled account, none of which a docs-scoped (MCP) key can do) and remote config / credentials). Mintable only locally - an /api mint refuses it, so a stolen admin-scoped key can never self-replicate - and its irreversible verbs additionally need the host-only remote_admin_enabled switch.

Expiry. A key can carry an optional expiry: mint it with a lifetime and it stops working the moment the date passes, refused exactly like a revoked key (the same 401, so nothing ever reveals the key existed). A key minted without one never expires, and every key that already exists keeps working: expiry is opt-in. When the install sets apikey_max_age_days (blank by default = no maximum), new keys cannot be created with a longer lifetime or with no expiry.

The shared connector token (lsk_…) is not a scope but a different credential kind, and is rejected by connector, translation, job, capability, document and CLI routes.

Minting a key

Sign in, open Account, and create an API key. Tick “Documents scope” for a docs key and “Keys scope” for a keys key - one key can carry both, and with neither ticked you get an api-only key. (The Keys checkbox appears only while key-based projects are switched on.) Optionally enter Expires in (days) to give the key a lifetime; leave it blank for no expiry. The full lsu_… value is shown once - copy it immediately; only its hash is stored. Revoke from the same page. The key list shows each key's expiry and marks it expired once the date passes.

RBAC & scoping notes

  • When the login wall is off (single-operator), role gates are a no-op - every predicate short-circuits to allowed.
  • When on, the same role predicates as the web UI apply. The Gate column below names the minimum role: write = can_write (≥ translator), manage = can_manage (≥ manager), tune-ai = can_tune_ai (admin or linguist), admin = is_admin.
  • Where the Gate column names a scope instead of a role, the scope is the whole gate: api = any authenticated key (the base grant every key carries), no docs/keys scope and no role check, read = a docs-scoped key with no further role check, docs = the same for the document front door, keys = a keys-scoped key with no role check (its writes additionally need can_write, marked keys+write), none = no authentication at all. A role gate always sits on top of the scope gate: a tune-ai row still needs the scope its group requires.
  • Every row is org- and (where applicable) customer-bound. A row in another org/customer returns 404 (never 403) so ids are not enumerable.
  • Shared items are read-only for a customer-bound account: it can open and use global workflows, groups, prompt templates, style guides and evaluation datasets and the org's language sets, but every change to one (rename, step edit, approve, delete, add to a group, gold or rules import, reference edit) answers 403. A language pair it adds to a shared group is its own customer's variant: it runs for that customer's documents only. It changes only its own customer's items. Cloning a global workflow, or creating a workflow or group with no customer, gives the account its own customer's copy.
  • The inbound document API is rate-limited per identity (429 with Retry-After); bodies are size-capped.
