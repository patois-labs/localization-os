# Localization OS 1.3.0

Release 1.3.0 moves the Bilingua parsing engine to 0.10.0 and carries a round of base image and dependency
security updates. It adds one small, additive database migration.

## Highlights

- **Bilingua 0.10.0.** The parsing engine (`patois-labs/bilingua`, Apache-2.0) is pinned to 0.10.0, installed from
  PyPI with its two wheel hashes, for the same platforms as before: x86_64 Linux (glibc 2.28 or newer) and Windows
  x64. On any other platform the package is skipped and every format keeps its Python filter. The settings, the
  default (`bilingua_formats` = `all`) and the formats Localization OS routes to Bilingua are unchanged.
- **Stored documents keep working.** Under the Localization OS profile, 0.10.0 keeps the same profile version and
  every skeleton schema, so documents imported with 0.9.1 export with 0.10.0 without a re-import, apart from the
  rare inputs under Known limitations. A comparison of stored documents parsed by both versions (about 1,700
  real-world files plus the test fixtures) found two that differ.

## Security and dependency updates

- The container base images are re-pinned: `python:3.13-slim` to the 2026-11-22 digest (also in the Vendor Studio
  image) and `tailscale/tailscale` from v1.104.2 to v1.104.7.
- The runtime image's package list names `zlib1g`, so the Debian security update for it (CVE-2026-85091) is
  installed even when the base image still carries the older build.
- `pyasn1` moves from 0.6.4 to 0.6.5.

## For developers

- `run_completion` takes an optional `history` (earlier chat turns, placed between the system message and the new
  prompt) for multi-turn callers. Every provider sends a byte-identical request when it is absent, and nothing in
  the core passes it; a provider that cannot take chat turns receives them flattened into its prompt.
- Workflow steps gain two inert columns, `doc_agent_mode` and `doc_agent_chunk`, used by an add-on that is not part
  of this edition. They default to empty and survive workflow copies. No door in this edition (web, API, CLI, MCP)
  sets them, a step save that tries to set a mode is refused, and every step runs per segment as before.

## Upgrade notes

1. Back up first, with the app stopped (`loc-tms db backup-full`). Rolling back after the migration ran means
   restoring this backup.
2. Refresh the dependencies: `pip install -r requirements.lock`. This installs `bilingua` 0.10.0 on x86_64 Linux
   and Windows x64 and `pyasn1` 0.6.5.
3. The migration runs on its own at the first start (`init_db` runs `alembic upgrade head`; the container
   entrypoint does the same on Postgres). One new revision, `a6d2e9b4c1f7`, on top of 1.2.0's head
   `e5a1c9d3b7f2`: it adds the two step columns above (`doc_agent_mode` not null with an empty default,
   `doc_agent_chunk` nullable). Existing steps read empty and behave exactly as before.
4. In the container, rebuild the image without a stale layer cache, so the re-pinned bases and the Debian security
   updates land. The build checks that `bilingua` imports on x86_64.

## Known limitations

- An HTML `<title>` or `<textarea>` is now written as typed: a translation that contains `&`, `<` or `>` there
  exports differently from 1.2.0.
- A document imported with 0.9.1 asks for a re-import at export when it has a title or textarea holding markup (for
  example a `<BR>` inside a `<title>`, now read as text), an XLSX with a repeated cell reference, a second byte order
  mark (DOCX, PPTX, XLSX, XLIFF) or a beta-namespace XLSX root. The comparison above found only the `<BR>` case.
- A very large email (.eml) can now be refused by the input limits, at upload and at export; a stored 0.9.1
  document of that size fails at export with the limit message, and a re-import is refused the same way.
- An image scan of this release's Dockerfile still flags CVE-2026-78661 in the `golang.org/x/net` copy inside the tailscale binaries
  (v1.104.7 is the newest stable release). It applies only when Tailscale is turned on with an auth key.
- The known output differences between Bilingua and the Python filters listed in the 1.2.0 notes still apply.
